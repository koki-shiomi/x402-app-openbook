# 刻印の検証手順

公開されている日次レコードが、取得時から書き換えられていないことを、第三者が確かめるための手順である。本システムのコードを実行せず、ブロックエクスプローラと SHA-256 を算出する一般的な道具だけで判定できる。

## 前提

| 項目 | 値 |
| --- | --- |
| チェーン | Arc Testnet（チェーン ID `5042002`） |
| 刻印のコントラクト | `0xC039722204Dde6DF3dFb48a9a3068163d30b997a` |
| エクスプローラ | https://testnet.arcscan.app/address/0xC039722204Dde6DF3dFb48a9a3068163d30b997a |
| ハッシュ | SHA-256（レコードのバイト列そのものに対して算出する） |

コントラクトはソースを検証済みで、エクスプローラから中身を読める。刻印は追加のみで、上書きと削除の手段を持たない。同じ対象日には、既に刻印されている最大のリビジョンより大きいリビジョンしか書き込めない。

## 手順

### 1. レコードのバイト列を入手する

有料 API から取得したレスポンス本文を、そのままファイルへ保存する。整形（インデントの追加、キーの並べ替え、末尾改行の追加）を行うとハッシュが変わるため、受け取ったバイト列を一切変更しない。

```bash
curl -s <レコードの URL> -o record.json
```

### 2. ハッシュを算出する

```bash
sha256sum record.json
```

出力は `0x` を伴わない 64 桁の 16 進数である。エクスプローラは `0x` つきで表示するため、比較するときは接頭辞の有無を揃える。

### 3. 対象日とリビジョンを読み取る

レコードの `date` と `revision` を見る。対象日は `YYYY-MM-DD` 形式だが、コントラクトは `YYYYMMDD` 形式の整数で保持している。

| レコードの `date` | コントラクトへ入力する値 |
| --- | --- |
| `2026-09-13` | `20260913` |

### 4. コントラクトへ照会する

エクスプローラのコントラクトの画面で **Contract → Read Contract** を開き、次の 2 つを呼ぶ。トランザクションの送信は不要で、ウォレットの接続も要らない。

| 関数 | 入力 | 返る値 |
| --- | --- | --- |
| `hashOf` | 対象日（`20260913`）、リビジョン | そのリビジョンに刻印されたハッシュ。未刻印ならすべて 0 |
| `latestRevisionOf` | 対象日（`20260913`） | その対象日に刻印された最大のリビジョン番号。刻印がなければ 0 |

コマンドで照会する場合は次のとおり。

```bash
cast call 0xC039722204Dde6DF3dFb48a9a3068163d30b997a \
  "hashOf(uint32,uint32)(bytes32)" 20260913 2 --rpc-url https://rpc.testnet.arc.io
cast call 0xC039722204Dde6DF3dFb48a9a3068163d30b997a \
  "latestRevisionOf(uint32)(uint32)" 20260913 --rpc-url https://rpc.testnet.arc.io
```

### 5. 分類を判定する

| 分類 | 条件 | 意味 |
| --- | --- | --- |
| **現行** | `hashOf` が手順 2 の値と一致し、リビジョンが `latestRevisionOf` と等しい | その対象日の現在の値として刻印されている |
| **履歴** | `hashOf` が手順 2 の値と一致し、リビジョンが `latestRevisionOf` より小さい | 刻印後に訂正された、過去の値である |
| **未刻印** | `hashOf` がすべて 0 | 刻印による証明がない |
| **不一致** | `hashOf` が 0 ではなく、手順 2 の値と一致しない | 刻印後にバイト列が変わっている |

## 判断の補足

- **同じ日に複数の刻印があるのは正常である。** 提供元が推定値を後から調整するため、公開後に値が変わることがある。値が変わると訂正リビジョンが追加され、あらためて刻印される。最大のリビジョンが現行の値で、それより小さいリビジョンは訂正の履歴である
- **未刻印はただちに改ざんを意味しない。** 刻印は収集の直後に行うが、失敗すると次の実行まで未刻印のままになる。また、刻印までに複数回訂正された日は、途中のリビジョンが刻印されないことがある
- **`latestRevisionOf` が返すリビジョンのレコードが公開されていない場合は、運営者に照会してほしい。** 刻印の鍵が漏洩した場合、存在しないリビジョンが刻印されうる。その状態では、本物の最新リビジョンが「履歴」と判定される
