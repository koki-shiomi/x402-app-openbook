# financial-record Specification

## Purpose

1日分の収益と費用を表す「日次財務レコード」の構造と、常に同一のバイト列へ直列化するための正準表現を定める。このバイト列がハッシュ刻印の対象であり、かつ有料 API が返す公開形式そのものとなる。

## Requirements

### Requirement: 日次財務レコードの構造

システムは、1 暦日分の収益と費用を 1 件の日次財務レコードとして表現しなければならない（SHALL）。レコードは以下を含む。

| 項目 | 内容 |
| --- | --- |
| `schemaVersion` | レコード形式のバージョン識別子 |
| `date` | 対象日（UTC の暦日、`YYYY-MM-DD` 形式） |
| `revision` | 同一日に対する通し番号（1 始まり） |
| `costs` | 費用エントリの配列 |
| `revenues` | 収益エントリの配列 |
| `incomplete` | 取得できなかった対象の配列（種別・識別子・理由） |
| `totals` | 費用合計・収益合計・損益の集計値（すべて JPY 建て） |
| `exchangeRates` | 当レコードで適用した為替レートの一覧 |
| `generatedAt` | レコード生成時刻（UTC、RFC 3339 形式） |

レコードは確定状態（暫定・確定）を持たない。取得元の多くは値を後から改訂するため、レコード単位の確定状態は実態を表せない。値がどの程度確かなのかは、後述するエントリ単位の取得方式と改訂可能性が表す。

対象日を UTC の暦日とするのは、費用の主要な取得元が UTC 日次で集計されており、他のタイムゾーンへ変換すると実測値を按分せざるを得なくなるためである。取得元が別のタイムゾーンで集計している場合は、そのタイムゾーンをエントリに記録して差異を明示する。

#### Scenario: 収益・費用が存在する日のレコード

- **WHEN** 対象日に費用エントリと収益エントリがいずれも存在する
- **THEN** レコードは全必須項目を持ち、`totals` は各エントリの合計と一致する

#### Scenario: 収集対象が 1 件も存在しない日のレコード

- **WHEN** 対象日に費用エントリも収益エントリも存在しない
- **THEN** `costs` と `revenues` は空配列となり、`totals` はすべて 0 となる

#### Scenario: 対象日がUTC暦日として妥当でない

- **WHEN** `date` が `YYYY-MM-DD` 形式でない、または実在しない日付である
- **THEN** レコードは不正として拒否される

### Requirement: エントリの取得方式と改訂可能性

費用エントリと収益エントリは、金額に加えて、その金額がどのように得られたか（取得方式）と、提供元が後から値を改訂しうるか（改訂可能性）を保持しなければならない（SHALL）。取得方式は次の 3 種類とする。

| 取得方式 | 意味 |
| --- | --- |
| `measured` | 提供元の API から取得した実際の課金額または収益額 |
| `derived` | 提供元から取得した使用量に、設定した単価を適用して算出した金額 |
| `estimated` | 設定した月額プラン費用を対象月の日数で日割りした金額 |

`derived` および `estimated` のエントリは、算出根拠（適用した単価または月額、対象月の日数、使用量）を併せて保持しなければならない（SHALL）。無料プランのため費用が発生しない提供元は、月額 0 円の `estimated` として記録し、プラン名を算出根拠に含める。

改訂可能性は、提供元が確定値を提供せず後から値を書き換えうる場合に真としなければならない（SHALL）。広告収益のように恒久的に推定値であり続ける取得元があるため、レコード単位ではなくエントリ単位で表す。

これらを保持するのは、公開された数値のうちどれが実測でどれが推定か、どれが今後変わりうるかを、利用者がレコードだけから判別できるようにするためである。

#### Scenario: 実測値のエントリ

- **WHEN** 提供元の API から確定した課金額を取得できた
- **THEN** 当該エントリの取得方式は `measured`、改訂可能性は偽となり、算出根拠は含まれない

#### Scenario: 後から改訂されうるエントリ

- **WHEN** 提供元が推定値のみを提供し、値を後から改訂する
- **THEN** 当該エントリの改訂可能性は真として記録される

#### Scenario: 無料プランで費用が発生しない提供元

- **WHEN** 提供元が無料プランで課金が発生しない
- **THEN** 当該エントリの取得方式は `estimated`、金額は 0 となり、プラン名と月額 0 円が算出根拠として記録される

#### Scenario: 取得方式が欠落している

- **WHEN** エントリに取得方式または改訂可能性が指定されていない
- **THEN** レコードは不正として拒否される

### Requirement: 欠測の記録

取得元からデータを取得できなかった場合、システムは当該対象を `incomplete` に、種別・識別子・理由とともに記録しなければならない（SHALL）。取得できなかった対象を金額 0 のエントリとして記録してはならない（MUST NOT）。

欠測を 0 円として扱うと、実際には費用や収益が発生していたかもしれない日が「発生しなかった日」として公開される。無料プランのため実際に 0 円である場合（前項の `estimated`）とは区別しなければならない。

#### Scenario: 取得元の障害による欠測

- **WHEN** ある取得元への問い合わせが失敗した
- **THEN** 当該取得元が理由とともに `incomplete` に記録され、`costs` にも `revenues` にも 0 円のエントリは追加されない

#### Scenario: 欠測がない場合

- **WHEN** すべての取得対象からデータを取得できた
- **THEN** `incomplete` は空配列となる

### Requirement: 金額の表現

すべての金額は 10 進小数を文字列として表現しなければならない（SHALL）。浮動小数点数を用いてはならない（MUST NOT）。小数桁数は通貨ごとに固定し、JPY は 2 桁、USD は 6 桁とする。

外貨建ての金額は、原通貨コード（ISO 4217）・原通貨での金額・適用した為替レート・JPY 換算後の金額をすべて保持しなければならない（SHALL）。これにより、公開されたレコードだけから換算を再計算できる。

#### Scenario: USD建て費用の記録

- **WHEN** USD 建ての費用 0.012345 ドルを記録する
- **THEN** 原通貨 `USD`、原金額 `"0.012345"`、適用レート、JPY 換算額が文字列としてすべて保持される

#### Scenario: JPY建て収益の記録

- **WHEN** JPY 建ての収益を記録する
- **THEN** 原通貨は `JPY`、換算は行われず、JPY 換算額は原金額と一致する

#### Scenario: 金額が数値型で与えられた

- **WHEN** 金額が文字列ではなく数値型で与えられた
- **THEN** レコードは不正として拒否される

### Requirement: 正準JSON表現

システムは、同一内容の日次財務レコードから常に同一のバイト列を生成しなければならない（SHALL）。直列化は RFC 8785（JSON Canonicalization Scheme）に従う。加えて、配列要素の順序を内容から決定するため、費用エントリと収益エントリは（提供元識別子, 費目識別子）の昇順、`incomplete` は（種別, 識別子）の昇順、為替レートは通貨ペアの昇順で並べなければならない（SHALL）。

この正準バイト列が、ハッシュ刻印の対象および有料 API のレスポンス本文となる。

#### Scenario: 同一内容から同一バイト列が得られる

- **WHEN** 同じ内容のレコードを、項目の生成順序を変えて 2 回直列化する
- **THEN** 生成されたバイト列は完全に一致する

#### Scenario: 内容が 1 文字でも異なれば結果が変わる

- **WHEN** レコードの金額を最小桁だけ変更して直列化する
- **THEN** 生成されたバイト列は変更前と異なる

#### Scenario: 配列の並びが入力順に依存しない

- **WHEN** 費用エントリを異なる順序で与えた 2 つのレコードを直列化する
- **THEN** 規定の並び順に整列され、同一のバイト列が得られる

### Requirement: スキーマバージョンの明示

すべてのレコードは `schemaVersion` を含まなければならない（SHALL）。レコードの構造または正準表現の規則を変更する場合は `schemaVersion` を更新しなければならない（SHALL）。過去に生成済みのレコードを新しいバージョンへ書き換えてはならない（MUST NOT）。

刻印済みのハッシュは生成時点の形式に依存するため、バージョンを併記しなければ後から検証を再現できない。

#### Scenario: 検証時のバージョン参照

- **WHEN** 過去のレコードを取得して正準バイト列を再生成する
- **THEN** レコードに記録された `schemaVersion` に対応する規則が適用され、生成時と同一のバイト列が得られる

### Requirement: 集計値の整合性検証

システムは、レコードを保存する前に `totals` が明細から再計算した値と一致することを検証しなければならない（SHALL）。一致しない場合はレコードを保存してはならない（MUST NOT）。`incomplete` が空でない場合、`totals` には欠測を含むために完全ではない旨を示さなければならない（SHALL）。

#### Scenario: 集計値が明細と一致する

- **WHEN** 費用合計・収益合計・損益がいずれも明細から再計算した値と一致する
- **THEN** レコードは妥当と判定される

#### Scenario: 集計値が明細と一致しない

- **WHEN** `totals` の費用合計が明細の合計と一致しない
- **THEN** レコードは不正として拒否され、保存されない
