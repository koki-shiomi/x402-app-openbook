# provider-credentials Specification

## Purpose

各提供元の認証情報に求める権限と、権限の範囲内でも呼び出してはならないエンドポイントを定める。費用を公開するシステム自身が、認証情報の漏洩によって費用を発生させられたり、個人情報を露出したりしない状態を保つ。

## Requirements

### Requirement: 読み取り専用の認証情報を用いる

システムは、各提供元の認証情報として、費用の確認に必要な読み取り権限のみを持つものを用いなければならない（SHALL）。リソースの作成・変更・削除ができる認証情報を用いてはならない（MUST NOT）。ただし、提供元が読み取り専用の権限を提供していない場合（Claude・Resend）と、運用上の判断で他用途の認証情報を兼用する場合（Cloudflare）は、「権限を限定していない認証情報の明示」に従う。

| 提供元 | 求める権限 |
| --- | --- |
| Cloudflare | 請求情報の読み取り（デプロイ用のトークンと兼用しており、Workers・R2 の編集権限も持つ） |
| Supabase | 読み取り専用のアクセストークン |
| Resend | `full_access` のキー（読み取り専用の権限が提供されていない） |
| Claude | Admin キー（権限を絞る手段が提供されていない） |
| AdMob | `admob.report` スコープの OAuth リフレッシュトークン（詳細は「AdMob の認証方式と権限」） |

Cloudflare と Supabase については、必要なエンドポイントがすべて読み取り権限のみで取得できることを実測で確認している。

#### Scenario: 書き込み権限のない認証情報での収集

- **WHEN** Cloudflare と Supabase について、読み取り専用の認証情報で費用収集を実行する
- **THEN** 必要な情報をすべて取得できる

### Requirement: 権限を限定していない認証情報の明示

Claude の Admin キーはスコープを選択できず、組織のすべての管理操作を行える。Resend の API キーは `full_access` と `sending_access`（送信のみ）の 2 種類しかなく、送信数の取得には `full_access` が必要である。システムは、これらの認証情報が他と異なり権限を限定できないことを、運用手順として記録しなければならない（SHALL）。Claude の Admin キーは有効期限を設定して発行しなければならない（SHALL）。

Cloudflare のトークンは請求情報の読み取りに限定して発行できるが、運用上の判断により、Workers・R2 の編集権限を持つデプロイ用のトークンを兼用する。システムは、この認証情報が権限を限定しておらず、デプロイ用と兼用している旨を、同様に運用手順として記録しなければならない（SHALL）。

#### Scenario: Admin キーの発行

- **WHEN** Claude の Admin キーを発行する
- **THEN** 有効期限が設定され、他の認証情報と権限の性質が異なる旨が記録される

#### Scenario: Resend のキーの発行

- **WHEN** Resend の API キーを発行する
- **THEN** 権限を限定できない認証情報である旨が記録される

#### Scenario: Cloudflare のトークンの兼用

- **WHEN** Cloudflare のデプロイ用のトークンを費用収集にも用いる
- **THEN** 権限を限定していない認証情報である旨と、デプロイ用と兼用している旨が記録される

### Requirement: 権限内でも呼び出さないエンドポイント

システムは、認証情報の権限の範囲内であっても、費用の確認に不要な個人情報を返すエンドポイントを呼び出してはならない（MUST NOT）。

Cloudflare の請求プロフィールは請求情報の読み取り権限で取得でき、氏名・住所・請求先メールアドレスを返す。権限設定では防げないため、呼び出すエンドポイントを実装で限定する。

#### Scenario: 請求プロフィールを呼び出さない

- **WHEN** Cloudflare から費用情報を取得する
- **THEN** サブスクリプション・従量課金・請求実績のみが呼び出され、請求プロフィールは呼び出されない

### Requirement: 認証情報が未設定の場合の扱い

いずれかの提供元の認証情報が設定されていない場合、システムは当該提供元の収集を欠測として記録しなければならない（SHALL）。認証情報がないことを 0 円として記録してはならない（MUST NOT）。

#### Scenario: 認証情報の欠落

- **WHEN** ある提供元の認証情報が設定されていない
- **THEN** 当該提供元が理由とともに欠測として記録され、0 円の費用エントリは作成されない

### Requirement: AdMob の認証方式と権限

システムは、AdMob API を OAuth 2.0 のリフレッシュトークンで認証しなければならない（SHALL）。要求するスコープは `admob.report` のみとし、`admob.readonly` を要求してはならない（MUST NOT）。

AdMob API はサービスアカウントに対応しておらず、アカウント所有者の同意に基づく OAuth 2.0 の認証のみを受け付ける。`admob.report` で閲覧できるのは収益レポートと、パブリッシャー ID・レポートタイムゾーン・通貨に限られる。`admob.readonly` は在庫やメディエーションの設定を含むすべての AdMob データを閲覧できる。いずれも閲覧専用のスコープである。

#### Scenario: 収益レポートのスコープでの収集

- **WHEN** `admob.report` スコープのみを持つリフレッシュトークンで収集を実行する
- **THEN** 対象日の収益と、アカウントのレポートタイムゾーンおよび通貨を取得できる

### Requirement: リフレッシュトークンの発行条件

AdMob のリフレッシュトークンは、OAuth 同意画面の公開ステータスを本番とした上で発行しなければならない（SHALL）。システムは、この発行条件と再発行時の注意点を運用手順として記録しなければならない（SHALL）。

外部ユーザー向けの同意画面がテスト状態のまま発行したリフレッシュトークンは、7 日で失効する。このほか、6 か月使われないトークンは失効し、同一の Google アカウントと OAuth クライアントの組で 100 件を超えて発行すると、最も古いトークンが警告なく無効になる。

#### Scenario: リフレッシュトークンの発行

- **WHEN** AdMob のリフレッシュトークンを発行する
- **THEN** 同意画面の公開ステータスが本番であり、発行条件と再発行時の注意点が記録される

### Requirement: リフレッシュトークンが使えない場合の扱い

リフレッシュトークンが失効または取り消されていてアクセストークンを取得できない場合、システムは AdMob の収集を欠測として記録し、トークンの再発行が必要である旨を理由に含めなければならない（SHALL）。

失効は収集の失敗としてしか現れないため、理由から原因と対処が分からなければ、欠測が続く原因の特定に時間がかかる。

#### Scenario: 失効したリフレッシュトークン

- **WHEN** 失効したリフレッシュトークンで収集を実行する
- **THEN** AdMob が欠測として記録され、理由にトークンの再発行が必要である旨が含まれる。他の取得元の収集は影響を受けない
