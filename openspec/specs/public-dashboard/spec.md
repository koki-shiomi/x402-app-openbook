# public-dashboard Specification

## Purpose

有料 API で何が取得できるのかを、ブラウザで実際に 1 日分を購入して確かめられるようにする。取得したバイト列はその場でチェーン上の刻印と照合し、第三者による検証が実際に成立することを示す。日次データの主たる取得経路は API そのものであり、この画面はその内容を確かめるためのものである。

## Requirements

### Requirement: 取得元の限定

システムは、表示するすべての財務データを有料 API から取得しなければならない（SHALL）。保存物へ直接アクセスしてはならず（MUST NOT）、API を経由しない別の取得経路を設けてはならない（MUST NOT）。

利用者が API から得られるものと画面に映るものが一致していなければ、画面は API の内容を確かめる用をなさない。運営者だけが見られる経路があると、公開しているデータと実際のデータが異なる余地が生まれる。

#### Scenario: 表示したデータの出どころ

- **WHEN** 画面に財務データが表示されている
- **THEN** その内容は有料 API の応答から得たものであり、利用者が同じ要求を行えば同じ内容を得られる

### Requirement: 支払いなしで見られる範囲

システムは、支払いなしで取得可能な対象日の一覧を表示しなければならない（SHALL）。一覧には対象日とリビジョン番号のみを示し、金額を示してはならない（MUST NOT）。

金額を支払いなしで示すと、有料 API が金額を有料としている前提が画面側から崩れる。

#### Scenario: 支払い前の表示

- **WHEN** 支払いを行わずに画面を開く
- **THEN** 取得可能な対象日とリビジョン番号の一覧が表示され、金額はどこにも表示されない

### Requirement: ウォレットによる支払い

システムは、利用者のブラウザのウォレットを用いて支払いを行わなければならない（SHALL）。秘密鍵を画面へ入力させてはならず（MUST NOT）、システムが秘密鍵を保持してはならない（MUST NOT）。

署名に用いる EIP-712 のドメインと有効期間は、API が返す支払いの条件から取り出さなければならない（SHALL）。画面に固定で持ってはならない（MUST NOT）。

決済の取次が広告する値と一致しない条件で署名すると受理されない。条件は API が組み立てて返すため、画面はそれをそのまま用いる。

#### Scenario: 支払いの実行

- **WHEN** 対象日を選んで支払いを行う
- **THEN** ウォレットが署名を求め、署名した支払いを添えた要求で当該日のレコードが返る

#### Scenario: 秘密鍵の非保持

- **WHEN** 画面を操作する
- **THEN** 秘密鍵の入力を求められることはなく、署名はウォレットの中で行われる

### Requirement: 支払いの事前条件の提示

システムは、支払いを行えない状態にある場合、その理由と必要な操作を示さなければならない（SHALL）。理由を示さずに失敗させてはならない（MUST NOT）。

| 状態 | 示す内容 |
| --- | --- |
| ウォレットが未接続 | 接続が必要であること |
| 接続先のチェーンが決済のネットワークと異なる | 切り替えが必要であること |
| 決済の取次に預けた残高が価格に満たない | 預け入れが必要であることと、画面から預け入れる手段 |
| 支払い元が受取先と同じアドレス | 別のアドレスが必要であること |

決済の取次は、資産を保有しているだけでは決済を成立させず、事前の預け入れを要する。また支払い元と受取先が同一の支払いを拒む。いずれも署名を終えてから失敗するため、事前に示さなければ利用者は原因を特定できない。

#### Scenario: 預け入れが足りない

- **WHEN** 決済の取次に預けた残高が価格に満たない状態で支払いを試みる
- **THEN** 署名を求める前に、預け入れが必要であることと、画面から預け入れる手段が示される

#### Scenario: チェーンが異なる

- **WHEN** 決済のネットワーク以外へ接続したウォレットで支払いを試みる
- **THEN** 切り替えが必要であることが示される

### Requirement: 決済に使える残高の確認と預け入れ

システムは、接続したアドレスが決済に使える残高を表示しなければならない（SHALL）。表示するのは決済の取次へ預け入れた残高であり、ウォレットが保有する残高を決済に使える額として示してはならない（MUST NOT）。

残高が足りない場合、システムは画面の操作で預け入れを行えなければならない（SHALL）。預け入れは、事前に使用枠を与える別のトランザクションを要さない方式で行わなければならない（SHALL）。利用者に求める操作は、1 回の署名と 1 回のトランザクションの承認までとする。

預け入れる額は利用者が決められなければならない（SHALL）。

預け入れた額が決済に使えるようになるまで時間がかかる。システムは反映を待ち、待っていることと完了を示さなければならない（SHALL）。反映を待たずに完了として示してはならない（MUST NOT）。

ウォレットに資産を保有していても、取次へ預け入れていなければ決済は成立しない。この区別は利用者にとって分かりにくく、残高があるのに支払えない状態に見える。使える額を明示し、その場で預け入れられるようにする。

事前の使用枠を与える方式では、利用者がトランザクションを 2 回承認することになる。署名で使用枠を渡せる方式なら 1 回で済む。

#### Scenario: 決済に使える残高の表示

- **WHEN** ウォレットを接続する
- **THEN** 決済の取次へ預け入れた残高が表示される

#### Scenario: 画面からの預け入れ

- **WHEN** 額を指定して預け入れを行う
- **THEN** 1 回の署名と 1 回のトランザクションの承認で預け入れが完了し、決済に使える残高が増える

#### Scenario: 反映の待機

- **WHEN** 預け入れのトランザクションが確定した
- **THEN** 決済に使える残高へ反映されるまで待っていることが示され、反映された時点で完了が示される

#### Scenario: 預け入れの後の支払い

- **WHEN** 残高不足で支払えなかった後に、画面から預け入れて再び支払いを試みる
- **THEN** 事前条件を満たし、支払いへ進める

### Requirement: 1 日分の明細の表示

システムは、購入した対象日について、収益と費用の内訳・欠測・適用した為替レートを表示しなければならない（SHALL）。

各エントリには、取得元・取得方式（実測／導出／宣言）・提供元が後から値を改訂しうるかを示さなければならない（SHALL）。原通貨の金額と換算後の金額の双方を示さなければならない（SHALL）。

同じ金額でも、実測値か宣言値かで意味が異なる。取得方式を示さずに金額だけを並べると、確からしさの違いが失われる。

#### Scenario: 購入した日の表示

- **WHEN** 対象日を購入する
- **THEN** 収益と費用の各エントリが取得元・取得方式・改訂の可能性とともに表示され、欠測と適用した為替レートも表示される

#### Scenario: 欠測を含む日の表示

- **WHEN** 欠測を含む日を購入する
- **THEN** 欠測した取得元とその理由が表示され、欠測が 0 円として表示されることはない

### Requirement: 取得したバイト列の検証

システムは、取得したバイト列をブラウザ上で検証し、判定の分類を表示しなければならない（SHALL）。検証は `anchor-verification` が定める分類と規則に従わなければならない（SHALL）。

検証にはブラウザからチェーンへ直接照会した値を用いなければならない（SHALL）。API が応答ヘッダで添える刻印の情報を、照合の根拠として用いてはならない（MUST NOT）。

API が返した情報だけで検証すると、API の自己申告を確かめているにすぎない。チェーンを直接見て初めて、運営者を信頼せずに済む。

判定の根拠として、算出したハッシュ・チェーン上のハッシュ・照会先のチェーンとコントラクトを示さなければならない（SHALL）。

#### Scenario: 刻印済みのバイト列の検証

- **WHEN** 購入した対象日のバイト列を検証する
- **THEN** 「現行」と判定され、算出したハッシュとチェーン上のハッシュが一致していることが示される

#### Scenario: 判定の根拠の表示

- **WHEN** 検証の結果が表示されている
- **THEN** 算出したハッシュ・チェーン上のハッシュ・照会先のチェーンとコントラクトのアドレスが示される

### Requirement: 取得した内容を保存しない

システムは、取得したレコードのバイト列と明細を保存してはならない（MUST NOT）。画面を離れると失われることを、購入の前に示さなければならない（SHALL）。

有料 API は利用者を識別せず、支払い 1 回につき取得 1 回である。保存しないため、同じ日を再び表示するには再び支払う必要がある。これを購入の前に示さなければ、利用者は意図せず二重に支払う。

#### Scenario: 再読み込み後の表示

- **WHEN** 購入して明細を表示した後に画面を再読み込みする
- **THEN** 明細は失われ、一覧の表示に戻る

#### Scenario: 購入前の断り

- **WHEN** 購入の操作を行う前の画面を見る
- **THEN** 取得した内容が保存されず、再表示には再び支払いが必要であることが示されている

### Requirement: 接続の後に起きた失敗の扱い

ウォレットの接続に成功した後の処理が失敗した場合、システムは、接続そのものが失敗したかのように示してはならない（MUST NOT）。実際に起きた失敗の内容を示さなければならない（SHALL）。

失敗した時点で利用者が操作をやり直せる状態を保たなければならない（SHALL）。接続の操作を取り除いた後に失敗し、やり直す手段が残らない状態にしてはならない（MUST NOT）。

接続の直後には、チェーンの確認や残高の照会など、ウォレットや RPC への問い合わせが続く。これらは接続とは別の理由で失敗しうる。接続できたのに「接続できなかった」と示すと、利用者は原因を取り違え、しかも操作が消えていればやり直すこともできない。

#### Scenario: 接続の後の照会が失敗する

- **WHEN** ウォレットの接続に成功した後、残高の照会が失敗する
- **THEN** 接続できなかったという理由は示されず、実際に起きた失敗の内容が示される

#### Scenario: 失敗した後のやり直し

- **WHEN** 接続の後の処理が失敗した
- **THEN** 利用者は操作をやり直せる
