## Context

Sizet OpenBook は新規リポジトリであり、既存コードは存在しない。本チェンジは動作するデータ収集を持たない基盤層のみを対象とする。動機は [proposal.md - Why](proposal.md) を参照。

設計を規定する制約は次の 3 点である。

1. **ハッシュ刻印との整合**: 後続チェンジ④で日次レコードのハッシュを Arc テストネットへ刻む。第三者が「API から取得したデータ」と「チェーン上のハッシュ」を突き合わせて検証できる必要があるため、保存物・ハッシュ対象・公開物のバイト列が一致していなければならない。
2. **データ規模が極めて小さい**: 収集ソースは費用 4 件・収益 2 件で、1 日あたり数レコード、年間約 2,200 件。書き込みは 1 日 1 回のバッチのみ。
3. **本システム自体の運用費を抑える**: 収益と費用を公開するシステム自身が高い固定費を持つと、公開する数値の意味が薄れる。無料枠内での運用を前提とする。

## Goals / Non-Goals

**Goals:**

- 保存されたバイト列がそのままハッシュ対象かつ API レスポンスとなる構造を確立する
- 収集ソースを 1 件も持たない状態で、基盤単体を検証・デプロイできる状態にする
- 後続チェンジ②③が収集処理の追加のみで完結するインタフェースを定める

**Non-Goals:**

- 実際のプロバイダからの費用・収益取得（②③で実施）
- ハッシュの算出とチェーンへの刻印（④で実施）
- 外部への公開手段（⑤で実施）
- 失敗時のメール等による能動的な通知（ログ出力に留める。通知手段の追加は運用開始後に必要性を判断する）

## Decisions

### 決定 1: リレーショナルDBを使わず、Cloudflare R2 のみを保存先とする

日次レコードを正準 JSON のオブジェクトとして R2 に保存し、D1・KV・Supabase のいずれも用いない。

**理由:**

- ハッシュ対象と保存物が一致する。DB に正規化して保存すると、レコードを読み出してから再直列化する工程が挟まり、その工程が公開バイト列とハッシュ対象の同一性を左右する。オブジェクトとして保存すれば「取得したバイト列をそのままハッシュして照合する」という最も単純な検証手順が成立する
- 年間約 2,200 件という規模では SQL の集計能力を使う場面がない。期間集計は取得したレコードをメモリ上で合算すれば足りる
- スキーマ定義・マイグレーション・接続管理という構成要素が不要になる
- read-after-write と list-after-write がいずれも強整合であり（[R2 Consistency model](https://developers.cloudflare.com/r2/reference/consistency/)）、「保存 → ハッシュ算出 → 刻印」を 1 回のバッチで連続実行する処理と整合する

**検討した代替案:**

| 選択肢 | 無料枠 | 不採用の理由 |
| --- | --- | --- |
| D1（SQLite） | 5GB、読み 500 万行/日、書き 10 万行/日（[D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)） | 費用面の問題はないが、ハッシュ対象と保存形式が乖離する。この規模で SQL を導入する利点がスキーマ管理コストに見合わない |
| Workers KV | 1GB、読み 10 万/日、書き 1,000/日（[KV Pricing](https://developers.cloudflare.com/kv/platform/pricing/)） | 容量は足りるが結果整合であり、全世界への伝播に時間を要する。書き込み直後にハッシュ算出のため読み戻す処理と相性が悪い |
| Supabase（Postgres） | Sizet 本体で利用中 | D1 と同じ理由に加え、Sizet 本体の無料枠を消費し、公開対象である Sizet の費用に本システムの分が混入する |

R2 の無料枠はストレージ 10GB / Class A 100 万・Class B 1,000 万リクエスト/月（[R2 Pricing](https://developers.cloudflare.com/r2/pricing/)）であり、想定利用量に対して十分な余裕がある。

### 決定 2: 不変性は R2 の条件付き書き込みで担保する

既存キーへの書き込みを防ぐため、Workers の R2 バインディングにおける `put()` の `onlyIf` オプションで「オブジェクトが存在しないこと」を条件に指定する（[Workers API reference](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)）。

**理由:** 事前に `head()` で存在確認してから `put()` する方式は、確認と書き込みの間に別の実行が書き込む余地が残る。手動再実行と定期実行が同時刻に走る可能性があるため、書き込み操作自体を条件付きにする。

**注意点:** 条件付き `put()` の判定ロジックが逆転する不具合が過去に報告されている（[workers-sdk#6411](https://github.com/cloudflare/workers-sdk/issues/6411)）。実装時に「既存キーへの書き込みが確実に失敗すること」をテストで検証し、期待どおり動作しない場合は `head()` による事前確認と、書き込み後の内容照合を併用する。

### 決定 3: 対象日を UTC の暦日とする

レコードの `date` は UTC の暦日を表す。JST（Asia/Tokyo）は用いない。

**理由:** 費用の主要な取得元である Claude API の Usage & Cost API は UTC の日次バケットで集計値を返す（[Usage & Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)）。これを JST の暦日へ変換するには時間単位への按分が必要になり、実測値が推定値に変質する。取得元が返す粒度をそのまま保持することを優先する。

**タイムゾーンが異なる取得元:** AdMob のレポートはアカウント既定のタイムゾーンか `America/Los_Angeles` しか指定できず（[Generate reports](https://developers.google.com/admob/api/v1/reporting)）、UTC を選べない。収益の暦日境界は費用とずれる。按分すると推定値になるため按分は行わず、取得元が用いた集計タイムゾーンをエントリに記録して差異を明示する。日本語圏の利用者向けの表示は、フロントエンド（⑥）で基準を明記して行う。

### 決定 4: 正準表現は RFC 8785（JCS）に配列の並び順規則を加えたものとする

**理由:** JCS はオブジェクトのキー順序・文字列エスケープ・数値表現を規定するが、配列要素の順序は入力のまま保持する。費用エントリの配列は収集ソースの実行順に依存し得るため、内容から一意に定まる並び順を別途規定する必要がある。

**金額を文字列で保持する理由:** JCS は数値を ECMAScript の `Number` として直列化するため、10 進小数が 2 進浮動小数点を経由し、`0.1 + 0.2` 問題と同種の誤差が入り得る。金額は文字列の 10 進小数として扱い、演算は 10 進固定小数点で行うことで、直列化経路に数値変換を持ち込まない。

### 決定 5: 為替レートは Frankfurter（ECB 公表値）を用いる

対象日の USD/JPY レートを `api.frankfurter.dev` から取得する（[Frankfurter](https://frankfurter.dev/)）。

**理由:** API キーが不要で無料、出典が ECB の公表参照レートであり第三者が同じ値を再取得して検証できる。公開する財務データの換算根拠としては、出典が明示でき再現可能であることが精度より重要である。

**休場日の扱い:** ECB は営業日のみレートを公表するため、土日・祝日は対象日そのもののレートが存在しない。この場合は対象日以前で最新の公表日のレートを適用し、実際に適用したレートの公表日をレコードに記録する。対象日から決定的に定まるため、再実行しても同じ結果になる。

**検討した代替案:** 有料の為替 API は精度と時点指定の自由度で優るが、本システム自体の固定費を増やす。無料枠での運用という制約を優先した。

### 決定 6: 実行基盤は Cloudflare Workers + Cron Triggers とする

**理由:** Sizet 本体が Hono / Cloudflare Workers 構成であり、運用知見をそのまま流用できる。Cron Triggers で日次実行を賄え、⑤の有料 API と⑥のフロントエンドも同じ基盤上に配置できる。

**実行時刻:** UTC 06:00 に前日分を対象として実行する。Claude API の当日分バケットが確定し、かつ ECB の前日レート公表（16:00 CET）を過ぎた時刻を選ぶ。取得元ごとの確定タイミングは②③の実装時に検証し、必要なら調整する。

### 決定 7: 手動再実行は共有シークレットによる Bearer 認証で保護する

**理由:** 利用者は開発者本人 1 名であり、ユーザー管理の仕組みは不要。Workers の Secret に保管したトークンとの定数時間比較で判定する。将来的に運用者が増える場合は Cloudflare Access への移行を検討する。

### 決定 8: リポジトリは pnpm ワークスペースの単一構成とする

初期構成は `apps/api`（Worker）と `packages/shared`（レコード型・正準化・10 進演算）の 2 パッケージ。⑥のフロントエンドは `apps/web` として後から追加する。

**理由:** 正準化ロジックはバックエンドとフロントエンドの双方が必要とする。フロントエンドが取得したレコードを自前でハッシュ計算して検証できることが、このシステムの主張の要であり、共有パッケージとして切り出す前提を最初から置く。Turborepo は現時点のパッケージ数では設定コストに見合わないため導入しない。

### 決定 9: レコードに確定状態を持たせず、月次クローズを書き込みの締切とする

レコードは `provisional` / `finalized` のような確定状態を持たない。代わりに、月次クローズ（既定で翌月 6 日）でその月への書き込みを締め切り、クローズ済みの月を④のハッシュ刻印の対象とする。

**理由:** 主収益である AdMob は、日次の確定値を提供しない。API v1 のリソースは `accounts` / `accounts.apps` / `accounts.adUnits` / `accounts.networkReport` / `accounts.mediationReport` のみで、payments や transactions に相当するものが存在しないため（[REST リファレンス](https://developers.google.com/admob/api/reference/rest)）、確定額は自動取得できない。取得できるのは `ESTIMATED_EARNINGS`（推定値）だけで、無効なクリック・インプレッションの調整により月末まで確定せず、確定するのは翌月初に計上される月次の支払総額である（[Estimated vs finalized earnings](https://support.google.com/admob/answer/6147072?hl=en)）。

したがって「日次レコードを確定させる」という状態遷移は原理的に成立しない。レコード単位の確定状態を持たせると、AdMob を含む日はすべて永久に暫定となり、状態として機能しない。値の確かさはエントリ単位の取得方式と改訂可能性で表し、レコードには持たせない。

**刻印を月次に寄せる理由:** 推定値が最も動くのは出現からの 48 時間で、翌月 3 日の月次確定後はほぼ動かない（[データ更新頻度](https://support.google.com/admob/answer/13291097?hl=en)）。刻印をクローズまで遅らせることで、「刻印後に値が変わる」状況が構造的に起きなくなり、チェーン上は 1 日 1 ハッシュに保たれる。既定値を翌月 6 日とするのは、月次確定（翌月 3 日まで）に余裕を持たせるためである。

**検討した代替案:**

| 選択肢 | 不採用の理由 |
| --- | --- |
| 取得のたびに刻印する | 訂正履歴そのものが証跡になる利点はあるが、同一日のハッシュがチェーン上に複数並び、検証手順が「どのリビジョンを見るべきか」の判断を伴うようになる |
| 日次は常時刻印し、月次確定レコードを別に持つ | 最も正確だが、レコード型が 2 つに増える。月次収支は日次レコードの集計として算出できるため、保持する必要がない |
| すべて月次粒度にする | 刻印は年 12 回で最も単純になるが、確定性の利得がない。AdMob は月次でも API から確定額を取得できず、Resend と Supabase も月次にして確定するわけではない。一方で Claude API の日々の費用変動という、このシステムの中心的な情報を失う |

**月次収支の扱い:** 月次レコードは作らない。月次収支は日次レコードの集計として都度算出する。値を二重に持つと、日次の合計と月次の値が食い違ったときにどちらが正かを決める規則が必要になる。

### 決定 10: 認証情報は最小権限とし、0 円は推定ではなくプラン確認で裏付ける

各取得元の認証情報は、費用の確認に必要な読み取り権限のみに絞る。また、無料枠で運用している提供元の費用 0 円は、月額 0 円の日割りとして推定するのではなく、API で取得したプラン情報を算出根拠として記録する。

**理由:** 2026-09 に全提供元の API を実際に呼び出して確認した結果、当初「課金額を返す API がない」と想定していた提供元でも、プランや課金対象の有無は取得できることがわかった。設定ファイルに書いた月額から日割りするより、その日に API で確認したプランを根拠にするほうが、公開値の裏付けとして強い。

| 提供元 | 0 円の根拠として取得するもの | 必要権限 |
| --- | --- | --- |
| Cloudflare | `subscriptions` が空（Workers Paid 未契約）、`billable-usage` が空、`billing/history` に請求なし | Billing Read |
| Supabase | `organizations/{slug}` の `plan`、`projects/{ref}/billing/addons` の `selected_addons` が空 | **read-only PAT で足りることを実測済み** |
| Resend | 日別送信数（`emails/metrics?dimensions=period`）。無料プランは超過時に課金ではなく 429 で送信が止まる | 読み取り可能なキー |
| Claude | 費用そのものを実測するため 0 円の裏付けは不要 | Admin キー（**絞り込み不可**） |

**再収集できない期間の扱い:** 取得元には遡及制限がある（Resend は約 30 日、Cloudflare の `billable-usage` は 1 リクエスト 31 日以内）。月次クローズで前月の全日を再収集しようとすると、遡及制限を超える日が生じる。この場合は既存の最新リビジョンを維持し、再収集を試みなかった事実を実行記録に残す。クローズ日を遡及制限内へ前倒しする案は、広告収益の月次確定（翌月 3 日まで）より前になり、クローズの目的を損なうため採らない。

## Risks / Trade-offs

- **`schemaVersion` 確定後の変更コスト** → 形式を変えると過去の刻印済みハッシュとの照合手順がバージョンごとに分岐する。②③の収集ソースを実装する前に、必要な項目が揃っているかをレビューで確認する。特に「取得方式の区別」と「集計タイムゾーンの記録」は後から追加すると既存レコードとの互換性を失う
- **R2 の条件付き書き込みの挙動** → 決定 2 の注意点に記載。実装時にテストで検証し、期待どおりでなければ代替手段へ切り替える
- **欠測を抱えたままクローズされる** → 取得元の障害が月をまたいで続くと、欠測を含んだままクローズされ刻印される。クローズ前に `incomplete` を持つ日を一覧できるようにし、手動再実行で解消できる導線を用意する。それでも解消しない場合は欠測を明示したまま公開する（0 円として埋めない）
- **取得元の遡及制限により月次クローズ時に再収集できない期間がある** → Resend の日別メトリクスは約 30 日しか遡れず、翌月 6 日のクローズ時点で前月前半は取得できない。決定 10 のとおり、再収集できない日は既存の最新リビジョンを維持し、その事実を実行記録に残す。②③で各取得元の遡及可能期間を実測し、クローズ日との関係を確認する
- **Claude の費用額を 100 倍に誤る** → `cost_report` の `amount` は `currency: "USD"` と返るが実際の単位はセントである。そのまま USD として扱うと公開値が 100 倍になる。②の実装で単位変換のテストを必ず用意する。`raw/` に保存した生応答があるため、誤りは後から検証できる
- **Claude の Admin キーは権限を絞れない** → Console のキーはスコープを選択できず全権限を持つ（[Create an Admin API key](https://platform.claude.com/docs/en/manage-claude/admin-api-keys)）。他の取得元は読み取り専用に絞れるのに、Claude だけ絞れない。漏洩時の影響が最も大きい認証情報として扱い、有効期限を設定して定期的に更新する
- **権限内でも呼んではならないエンドポイントがある** → Cloudflare の `billing/profile` は Billing Read の範囲でありながら氏名・住所・請求先メールを返す。権限設定では防げないため、バッチが呼ぶエンドポイントを実装で限定する
- **Cloudflare の課金が発生したときの粒度が未確定** → 現在 `billable-usage` は空配列を返すため、charge period が日次かどうかを検証できない。課金が発生した時点で確認し、日次で取れなければ日割りの `estimated` に切り替える
- **UTC 基準の日付が日本の利用者に直感的でない** → 月次集計の境界が JST とずれる。加えて AdMob の収益は別タイムゾーンで集計されるため、費用と収益で暦日境界が一致しない。表示時に基準を明記して対応し、データ側では按分を行わない

## Migration Plan

新規プロジェクトのため移行対象はない。デプロイ手順は次のとおり。

1. R2 バケットを作成し、Worker にバインドする
2. Worker を Cron Triggers 付き（日次実行と月次クローズ）でデプロイする
3. 収集ソースが 0 件の状態で日次実行を動作させ、空レコードが生成・保存されることを確認する
4. 月次クローズを動作させ、対象月がクローズ済みとして記録され、以降その月への書き込みが拒否されることを確認する
5. 手動再実行エンドポイントの認証が機能することを確認する

ロールバックは Worker のデプロイを直前バージョンへ戻すことで行う。R2 に保存済みのオブジェクトは不変であり削除しないため、ロールバックによるデータ損失は生じない。ただし月次クローズの記録を取り消す手段は用意しない。誤ってクローズした場合は、その月を対象外として扱うか、`schemaVersion` を更新して別系列として作り直す。

## Open Questions

- **Cron Triggers の実行時刻（日次 UTC 06:00 / 月次クローズは翌月 6 日）が適切か**: 各取得元の値が確定する時刻は②③の実装時に実データで確認する。いずれも設定値であり、レコード形式に影響しないため後から調整できる
