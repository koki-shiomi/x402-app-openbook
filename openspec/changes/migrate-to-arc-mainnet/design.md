## Goals / Non-Goals

**Goals:**

- チェーン定義を集約し、API・画面・検証の接続先と署名のチェーン ID を揃える
- 旧データが再生成される競合を防ぎ、空のレコード保存先から通常の日次処理で再開する
- 再開後の実レコードで刻印・公開・検証・決済を確認する

**Non-Goals:**

- Testnet との切替機能、複数チェーンへの同時対応、Testnet への切り戻し
- 旧データの保存・移送・復元、旧対象日の再刻印
- 長期運用の資金確保、自動補充、残高監視機能の追加
- コントラクトの再配備、ダミーデータの本番刻印

## Decisions

### 決定 1: メインネットの定義を一箇所に置く

共有パッケージに `defineChain` による定義を置き、ID・通貨・RPC・エクスプローラを明示する。刻印のコントラクト・決済ネットワーク・資産・Gateway Wallet も共有のネットワーク設定に集約する。API の RPC とコントラクトは既存の設定経由で読み、公開する設定と一致することをリリース前に検証する。秘密鍵は共有設定へ含めない。

刻印の照会と送信は同じ定義を使用し、送信前に RPC が返すチェーン ID を照合する。Web のウォレット接続、預入れの EIP-712、検証用 reader も同じ定義を使用する。第三者検証の根拠となる RPC とコントラクトは引き続き公開設定から取り、API の自己申告だけには依存しない。

代替案は既存の固定値を個別に置き換える方式。取りこぼしや署名と接続先の不一致を避けるため採用しない。

### 決定 2: 旧開発データを削除し、メインネット専用の保存先にする

既存 R2 バケット `sizet-openbook-records` を再利用する。停止中に `records/`・`anchors/`・`raw/`・`runs/`・`collection-runs/`・`anchor-runs/`・`payments/` の旧開発データを削除する。旧決済記録を残すと、新しい収支の決済収益に混ざるため、これも削除対象とする。バケット本体と列挙した接頭辞以外のオブジェクトは対象外とする。

削除スクリプトは既定で対象のバケット・接頭辞・日付・キー・件数を表示するだけとする。全ページを列挙した具体的な対象一覧を作り、明示的にその一覧を確定してから削除する。途中失敗時は定期実行を停止したまま残存キーを再列挙して完了させる。退避コピーは作らない。

移行時に旧データを除去し、以後は Mainnet の書込みだけを許すことを公開境界とする。一覧には現在のキーと最新リビジョンの突き合わせを使用し、チェーン ID を読むための対象日ごとの追加 GET や公開用インデックスは導入しない。取得済みの刻印情報のチェーン ID とコントラクトはメインネット設定と整合することを確認する。

代替案は `retired/` への退避、チェーン別バケット、混在した刻印の動的な絞り込み。旧データを使わない方針に合わせ、移行・復元や複数チェーンの管理を追加しない。

### 決定 3: 最初の成功した前日収集から新しい稼働期間を始める

既存の `runCollection` は前日収集を先に実行し、再収集は保存済みレコードの最古日以降に限って行う。レコードが一件もなければ埋め戻しを行わない。この挙動を維持する。

再開後の最初の前日収集が成功したとき、その対象日を新しい稼働期間の始まりとする。削除一覧の最も新しい対象日より後の日が最初の前日収集の対象になるよう、再開する定期実行の日時を決める。同じ日の旧データを削除した直後に再生成することを防ぐためである。初回のリビジョンは 1 で、それより古い開発期間の日を自動で埋め戻さない。初回が失敗しても旧データを復元せず、次の前日収集の成功から始める。再開実行日時と最初に保存した対象日を記録する。

代替案は開始日を新しい設定値で持つ方式。既存の前日収集と最古日の規則で目的を満たすため、設定を追加しない。運営者の手動再実行は任意の日を扱える既存仕様を維持するが、移行作業では旧対象日の再収集を行わない。

### 決定 4: 書込みを止めてから一つのリリースで切り替える

定期実行の停止だけでは、実行中の処理や `/admin/rerun` が旧データを書き戻す可能性がある。一時的なメンテナンス用 Worker を公開し、収集・刻印・手動再実行・有料取得を停止する。停止前に始まった処理が終了したことも確認してから削除する。メンテナンスは一時的な配備手順として用意し、通常運用の恒久的な切替モードを増やさない。

停止中に削除とシークレット更新を行い、検証済みの Worker と静的資産を同じリリースで公開する。古いタブは旧 JavaScript を保持するため、購入・預入れの確認は再読み込みした画面で行う。

代替案は稼働したままシークレット・R2・画面を順番に変更する方式。ネットワークの不一致や旧データの再生成を防ぐため採用しない。

### 決定 5: 刻印と受取先を共用し、資金補充とソース公開検証を切替えの条件から外す

2026-10-04 の運営者の指示により、刻印の署名鍵と決済の受取先は既存 EOA `0xd77dd307A9E395fB2680011deeD994A27cf70d4b` を共用する。同一アドレスを拒否する検証は設けない。自動署名鍵が受取先も兼ねることを運用文書へ記録する。残高が不足した場合は既存の刻印失敗・再試行の仕組みで扱う。購入者と受取先が同じ場合の自己送金拒否は維持し、実決済の確認には別の買い手アドレスを使用する。

2026-10-02 の配備後に読み取った残高は約 `0.0877171 USDC`。これはその時点の観測値であり、切替え時に残高を読み直す。年間運用分の前払いは求めず、必要なら運営者が補充する。

ソース公開検証の未完了は記録し、承認後に後続作業として扱う。切替えの技術的な成立はコード配置・所有者・実データの刻印と読み取りで判定する。再配備は行わない。

代替案は年間資金の確保とソース検証の完了を必須とする方式。技術デモという運用目的に合わせて採用しない。

## Risks / Trade-offs

- 旧 R2 データの削除は復元できない → 実行前に具体的な対象一覧を確定する。旧データを保存しない合意に基づく一回限りの移行例外とし、新しい保存物の不変性は維持する
- 旧処理が削除後に書き戻す → 収集・刻印・手動再実行を停止し、実行中の処理の終了を確認する
- 途中失敗で公開設定が揃わない → メンテナンスを維持して修正し、Mainnet の整合性確認後に再開する
- 初回収集または刻印が失敗する → 未刻印の日は課金せず、既存の実行記録と再試行で扱う
- ガス残高が不足する → 運営者が必要に応じて補充する。保管済みレコードは維持する
- ソースが未検証のため第三者が実装を確認しにくい → 未検証と明記し、公開送信の承認後に検証する
- 本番 facilitator の広告が以前の観測と変わる → 切替え直前に `eip155:5042` の対応と `extra` を再確認し、署名条件と Web の Gateway Wallet を照合する

## Migration Plan

1. 仕様のテストを先に用意し、チェーン定義・決済・検証・削除スクリプト・メンテナンス手順を実装する。空の保存先からの収集と、削除後の 404 を確認する
2. 型検査・テスト・ABI・Cron・静的資産の検査を行う。公開文書も同じリリースでメインネットの値へ更新する
3. 配備済みコントラクトのコード・所有者・チェーン ID と残高を確認する。指定の受取先を確定し、本番 facilitator の広告と設定が一致することを確認する
4. メンテナンス版を公開し、定期実行・手動再実行・課金の停止と実行中処理の終了を確認する。削除対象の具体的な一覧を確定する
5. 一覧の旧データを削除し、対象接頭辞の残存がないことを確認する。削除日時・対象日・件数を記録する
6. シークレットを更新し、Worker・静的資産を同じメインネット版で公開する。設定の整合性を確認して日次処理を再開する
7. 初回収集前は一覧が空で旧対象日の取得が 404 であることを確認する。最初の前日収集と、その後の定期刻印で、Mainnet の receipt・`hashOf`・保存バイト列の SHA-256 の一致を確認する。削除した旧期間が埋め戻されないことも確認する
8. 再読み込みした画面から実際に 1 日分を購入し、本番の決済成立・明細表示・検証成功を確認する。実測結果を記録して正式仕様への反映とアーカイブへ進む

旧データの復元と Testnet への切り戻しは行わない。障害がある場合は書込み・課金を止め、メインネット設定を修正して再開する。ソース公開検証は承認後の後続作業とする。
