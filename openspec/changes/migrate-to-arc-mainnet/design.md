## Context

移行の動機は proposal.md の「Why」を参照。

実 API とチェーンに対して次を実測した（2026-09-22）。

| --- | --- | --- |
| チェーン ID | 5042002 | **5042** |
| RPC | `https://rpc.testnet.arc.io` | **`https://rpc.mainnet.arc.io`**（`eth_chainId` が `0x13b2` を返すことを確認） |
| エクスプローラ | `https://testnet.arcscan.app` | **`https://explorer.arc.io`** |
| USDC | `0x3600000000000000000000000000000000000000` | 同じアドレス。`name` は `USDC`、`version` は `2` で、いずれもテストネットと同じ |
| facilitator | `https://gateway-api-testnet.circle.com/v1/x402` | **`https://gateway-api.circle.com/v1/x402`** |
| Gateway Wallet | `0x0077777d7eba4688bdef3e311b846f25870a19b9` | **`0x77777777Dcc4d5A8B6E418Fd04D8997ef11000eE`** |

本番 facilitator の `/supported` は `eip155:5042` を含み、`extra` はテストネットと同じ形（`GatewayWalletBatched` / version `1` / `minValiditySeconds` 604800）である。**決済の署名の組み立て方は変わらない。**

viem には `arc`（id 5042）の定義があるが、**`rpcUrls` が空で、エクスプローラの定義もない**。テストネットで使っていた `arcTestnet` のようにそのまま渡せない。

刻印のガス代を実測した。`maxFeePerGas` は約 24 Gwei、ネイティブ通貨の桁数は 18。刻印 1 件あたり約 0.0018 USDC、1 日 1 回の運用で年間約 0.65 USDC。

## Goals / Non-Goals

**Goals:**

- チェーンに依存する値を設定へ集約し、移行後に旧いチェーンを指す箇所が残らないようにする
- 移行前の対象日を、公開の対象から外したうえで保存は続ける
- 実費が発生する鍵の扱いを、運用に要する範囲へ限定する

**Non-Goals:**

- 複数のチェーンへの同時対応。1 つの設定だけを持つ
- 価格の見直し。0.10 USDC のままとする
- 移行前のレコードの削除

## Decisions

### 決定 1: 移行前の日は、保存先を移して公開の対象から外す

移行の作業として、移行前の `records/{対象日}/` と `anchors/{対象日}/` を、公開の対象にならない接頭辞（`retired/records/`・`retired/anchors/`）へ移す。実行時にチェーン ID を読んで除外する方式は採らない。

一覧はキーの列挙だけで判定しており、刻印の本文は読んでいない。チェーン ID で除外するには対象日の数だけ本文を読むことになり、支払いのいらない一覧の経路が重くなる。保存先を移せば、一覧も取得も既存の判定のまま自然に対象外になる。

移行後、これらの日は「レコードが存在しない日」として扱われ、取得を試みると 404 が返る。移行前に取得できた日が取得できなくなる点は、proposal.md のとおり利用者から見た破壊的な変更である。

**代替案:**

- 実行時に刻印のチェーン ID を読んで除外する。判定は動的で正確だが、一覧の経路が対象日の数だけ本文を読むことになる
- 移行前のレコードを削除する。保存物を失う。検証の再現もできなくなる

なお、再収集の埋め戻しは「レコードが存在する最も古い日」を稼働期間の始まりとするため、移行前の日を移した後は、それらの日が埋め戻しの対象に戻ることはない。

### 決定 2: チェーンの定義を自前で持つ

viem の `arc` は `rpcUrls` が空であるため、`defineChain` でチェーン ID・通貨・RPC・エクスプローラを明示した定義を 1 箇所に置き、API・画面・共有パッケージがこれを使う。

`arcTestnet` を直接 import している箇所（`anchor/chain.ts`・`deposit.ts`・`reader.ts`）は、この定義に置き換える。固定値が散らばったまま移行すると、一部が旧いチェーンを向いたまま残る。

**代替案:**

- viem の `arc` に `rpcUrls` を差し込んで使う。定義の一部だけを上書きする形になり、エクスプローラの不足は別に補う必要がある

### 決定 3: 刻印の鍵と受け取りのアドレスを分ける

現行はいずれも `0xd77dd307A9E395fB2680011deeD994A27cf70d4b` である。移行にあたり、決済の受け取りは別のアドレスにする。刻印の鍵には、刻印に要する分（年間 1 USDC 程度）だけを保有させる。

刻印の鍵は日次で自動的に署名するため、Worker のシークレットとして常時利用できる状態にある。受け取った分をここへ集めると、漏洩したときに失う額が運用に要する額を超える。

### 決定 4: 移行は 1 回のデプロイで行い、その前に配備と資金を済ませる

順序は次のとおり。前段が終わるまで設定を切り替えない。

1. メインネットへ刻印のコントラクトを配備し、ソースを検証する
2. 刻印の鍵へ、刻印に要する USDC を入れる
3. 受け取り用のアドレスを用意する
4. 移行前の対象日を `retired/` へ移す
5. シークレットと実装の設定を切り替えてデプロイする

4 を 5 より先に行うのは、切り替えた直後に、旧いチェーンで刻印された日が一覧に残る時間を作らないためである。

## Risks / Trade-offs

- **移行前の日が取得できなくなる** → proposal.md に破壊的な変更として明記した。保存物は `retired/` に残り、必要なら戻せる
- **実費が発生する** → 刻印は年間 1 USDC に満たない。鍵が保有する額を運用に要する範囲へ限ることで、漏洩したときに失う額も同じ範囲に収まる
- **決済が実際の価値を持つ** → 価格は変えない。テストネットでの検証と同じ経路で成立することを、移行後に 1 回の支払いで確かめる
- **RPC の所在が公式ドキュメントで確認できていない** → `eth_chainId` が 5042 を返すことは実測した。公式の案内が見つかれば、それに合わせて見直す

## Migration Plan

上記の決定 4 の順序で行う。

切り戻しは、シークレットと実装の設定をテストネットへ戻し、`retired/` の保存物を元の接頭辞へ戻すことで可能である。メインネットで刻印した日は、戻した後は公開の対象から外れる。

反映後は、一覧が移行後の日だけを返すこと、移行前の日が 404 になること、刻印がメインネットで成立すること、実際の支払いが 1 回成立することを確認する。
