## Purpose

Claude API・Cloudflare・Resend・Supabase から日次の費用を取得し、取得方式と算出根拠つきの費用エントリへ変換する規則を定める。公開される金額のうちどれが実測でどれが推定かを、レコードだけから判別できる状態を保つ。

## ADDED Requirements

### Requirement: Claude API 費用の実測取得

システムは、Claude の Usage & Cost API から対象日の費用を日次バケットで取得し、費用エントリとして記録しなければならない（SHALL）。取得方式は `measured` とし、提供元が値を改訂しないため改訂可能性は偽としなければならない（SHALL）。

モデルおよび入出力の別ごとに費用エントリを分けなければならない（SHALL）。合算すると、どのモデルにいくらかかったかという公開データの主要な情報が失われる。

#### Scenario: 利用があった日の取得

- **WHEN** 対象日に Claude API の利用があった
- **THEN** モデル別・入出力別の費用エントリが作成され、取得方式は `measured`、改訂可能性は偽となる

#### Scenario: 利用がなかった日の取得

- **WHEN** 対象日に Claude API の利用がなかった
- **THEN** 費用エントリは作成されず、欠測としても記録されない

### Requirement: セント単位から USD への変換

Claude の Cost API が返す金額の単位はセントである。システムは、取得した値を 100 で除して USD へ変換した上で費用エントリに記録しなければならない（SHALL）。応答の値をそのまま USD として扱ってはならない（MUST NOT）。

応答の `currency` フィールドは `USD` を返すが、実際の単位はセントである。使用量レポートのトークン数と公開単価から計算した値と一致することを実測で確認している。変換を誤ると公開する費用が 100 倍になる。

#### Scenario: セント値の変換

- **WHEN** Cost API が `amount` として `1.0071`、`currency` として `USD` を返す
- **THEN** 費用エントリには USD 建てで `0.010071` が記録される

#### Scenario: 変換の検証

- **WHEN** 同一期間の使用量レポートからトークン数と公開単価で費用を算出する
- **THEN** 変換後の費用エントリの金額と一致する

### Requirement: 対象ワークスペースの限定

システムは、Claude の費用のうち sizet 専用ワークスペースに属する分のみを対象としなければならない（SHALL）。他のワークスペースに属する費用を含めてはならない（MUST NOT）。

Cost API は組織全体の費用を返し、API キー単位では絞り込めない。ワークスペース単位でしか分解できないため、対象ワークスペースを設定値として持ち、それ以外を除外する。

既定ワークスペースを対象とする場合、応答上の識別子は空値になる。設定値をそのまま空値にすると「既定ワークスペースを意図して選んだ」のか「設定し忘れた」のかを区別できないため、既定ワークスペースを指す明示的な設定値を用いなければならない（SHALL）。

#### Scenario: 複数ワークスペースが存在する場合

- **WHEN** 組織に対象ワークスペースと他用途のワークスペースが存在し、両方に費用がある
- **THEN** 対象ワークスペースの費用のみが費用エントリになる

#### Scenario: 既定ワークスペースを対象に指定した場合

- **WHEN** 既定ワークスペースを指す明示的な設定値が与えられている
- **THEN** 応答上の識別子が空値である費用のみが費用エントリになる

#### Scenario: 対象ワークスペースが設定されていない

- **WHEN** 対象ワークスペースの設定値そのものが与えられていない
- **THEN** 収集は失敗し、欠測として記録される。組織全体の費用を計上してはならない

### Requirement: Cloudflare 費用のプラン確認による裏付け

システムは、Cloudflare の費用が発生していないことを次の 3 点すべてで確認し、確認結果を算出根拠として記録しなければならない（SHALL）。

| 確認項目 | 判定 |
| --- | --- |
| サブスクリプション一覧 | すべての価格が 0 であること（Workers Paid などを未契約） |
| 従量課金の請求額 | 対象日を含む期間の全行の請求額の合計が 0 であること |
| 請求実績 | 対象日に請求が発生していないこと |

3 点すべてを満たす場合、金額 0 の費用エントリを取得方式 `estimated` として記録しなければならない（SHALL）。いずれかを満たさない場合、0 円として記録してはならない（MUST NOT）。

サブスクリプションと従量課金は、いずれも存在の有無では費用の発生を判定できないため、金額で判定する。R2 を有効にすると価格 0 のサブスクリプションが作成され、R2 の利用に対する課金は従量課金の請求額に現れる。従量課金は、無料枠に含まれる利用も請求額 0 の行として返す。価格または請求額を確認できないものが含まれる場合、0 であるとみなしてはならない（MUST NOT）。

#### Scenario: 無料枠内での運用

- **WHEN** サブスクリプションの価格がすべて 0、従量課金の請求額の合計が 0、対象日に請求がない
- **THEN** 金額 0 の費用エントリが作成され、3 点の確認結果が算出根拠に含まれる

#### Scenario: 無料枠に含まれる利用がある

- **WHEN** 従量課金に請求額 0 の行が含まれ、他の 2 点も満たす
- **THEN** 金額 0 の費用エントリが作成され、従量課金の行数と請求額の合計が算出根拠に含まれる

#### Scenario: 従量課金の請求額が発生している

- **WHEN** 従量課金の請求額の合計が 0 でない
- **THEN** 0 円として記録せず、費用が発生している旨を欠測として記録する

#### Scenario: 従量課金の請求額を確認できない

- **WHEN** 従量課金に請求額を持たない行が含まれる
- **THEN** 0 円として記録せず、欠測として記録する

#### Scenario: 価格 0 のサブスクリプションのみが存在する

- **WHEN** サブスクリプション一覧に価格 0 の契約のみが含まれ、他の 2 点も満たす
- **THEN** 金額 0 の費用エントリが作成され、サブスクリプションの件数とプラン名が算出根拠に含まれる

#### Scenario: 有料サブスクリプションが存在する

- **WHEN** サブスクリプション一覧に価格が 0 でない契約が含まれる
- **THEN** 0 円として記録せず、費用が発生している旨を欠測として記録する

#### Scenario: サブスクリプションの価格を確認できない

- **WHEN** サブスクリプション一覧に価格を持たない契約が含まれる
- **THEN** 0 円として記録せず、欠測として記録する

### Requirement: 従量課金の取得期間の分割

システムは、Cloudflare の従量課金を取得する際、1 回の要求で 90 日を超える期間を指定してはならない（MUST NOT）。90 日を超える期間を対象とする場合は分割して取得しなければならない（SHALL）。

提供元が 1 リクエストあたりの期間上限を設けており、超過すると要求が失敗する。

#### Scenario: 上限を超える期間の取得

- **WHEN** 90 日を超える期間の従量課金を取得する
- **THEN** 90 日以内の複数の要求に分割して取得される

### Requirement: Resend 費用のプラン宣言による記録

システムは、Resend の日別送信数を取得し、設定値として宣言されたプランとともに費用エントリの算出根拠に記録しなければならない（SHALL）。無料プランが宣言されている場合、金額 0 の費用エントリを取得方式 `estimated` として記録しなければならない（SHALL）。

課金額を返す API が存在せず、プラン判定に使えるヘッダは送信時のレスポンスにしか付かない。費用確認のためだけにメールを送信するのは本末転倒であるため、プランは設定値として宣言し、送信数を併記して判断材料とする。

#### Scenario: 無料プランが宣言されている場合

- **WHEN** 設定で無料プランが宣言され、対象日の送信数を取得できた
- **THEN** 金額 0 の費用エントリが作成され、プラン名と送信数が算出根拠に含まれる

#### Scenario: 有料プランが宣言されている場合

- **WHEN** 設定で有料プランが宣言されている
- **THEN** 宣言された月額を対象月の日数で日割りした費用エントリが作成される

### Requirement: Resend の遡及可能期間

システムは、Resend の日別送信数を取得できる期間を宣言しなければならない（SHALL）。宣言した期間より前の対象日については、取得を試みずに再収集できない旨を返さなければならない（SHALL）。

提供元が約 30 日より前の日付を指定しても直近の日付へ切り詰めるため、切り詰められた値を対象日の値として記録すると誤ったデータが公開される。

#### Scenario: 遡及可能期間内の取得

- **WHEN** 対象日が遡及可能期間内である
- **THEN** 対象日の送信数が取得される

#### Scenario: 遡及可能期間を超えた対象日

- **WHEN** 対象日が遡及可能期間より前である
- **THEN** 取得は試みられず、再収集できない旨が返る

### Requirement: Supabase 費用のプラン確認による裏付け

システムは、Supabase の組織プランと各プロジェクトの課金アドオンを取得し、確認結果を算出根拠として記録しなければならない（SHALL）。プランが無料であり、かつすべてのプロジェクトで課金アドオンが適用されていない場合に限り、金額 0 の費用エントリを取得方式 `estimated` として記録しなければならない（SHALL）。

#### Scenario: 無料プランかつアドオンなし

- **WHEN** 組織のプランが無料で、すべてのプロジェクトの課金アドオンが空である
- **THEN** 金額 0 の費用エントリが作成され、プラン名とアドオンの確認結果が算出根拠に含まれる

#### Scenario: 課金アドオンが適用されている

- **WHEN** いずれかのプロジェクトに課金アドオンが適用されている
- **THEN** 0 円として記録せず、費用が発生している旨を欠測として記録する

### Requirement: 現在の状態しか返さない提供元の遡及可能期間

システムは、現在の契約状態しか取得できない提供元（Supabase のプランと課金アドオン、Cloudflare のサブスクリプション）について、前日より前の対象日を取得できないものとして宣言しなければならない（SHALL）。

これらの API は過去の時点を指定する手段を持たない。過去日の再収集に現在の状態を適用すると、その日の実態と異なる判定になる。たとえば後から有料の契約を追加すると、無料だった過去日まで欠測に置き換わる。

#### Scenario: 前日を対象とした取得

- **WHEN** 前日を対象に取得する
- **THEN** 実行時点の状態を根拠として取得される

#### Scenario: 前日より前の対象日

- **WHEN** 前日より前の対象日を再収集する
- **THEN** 取得は試みられず、既存の値が維持される

### Requirement: 対象外とする費用

システムは、Cloudflare のドメイン登録費を費用エントリに含めてはならない（MUST NOT）。

ドメイン登録費はアプリの運用に応じて変動する費用ではなく、公開の目的である「アプリを動かすのにいくらかかっているか」とは性質が異なる。ただし公開する費用合計が提供元の請求実績と一致しなくなるため、対象外としている事実を利用者が知れる形で示さなければならない（SHALL）。

#### Scenario: ドメイン登録費の請求がある日

- **WHEN** 対象日にドメイン登録費の請求が存在する
- **THEN** 費用エントリには含まれず、対象外である旨が判別できる

### Requirement: 生応答の保存

システムは、各提供元から取得した応答を、認証情報を除いた上で保存しなければならない（SHALL）。応答に費用の確認に不要な個人情報が含まれる場合は、それも除いて保存しなければならない（SHALL）。

セント単位の変換など、取得値から公開値への加工を後から検証できるようにするため。Cloudflare の従量課金は各行のアカウント名に請求先のメールアドレスを含むが、判定に用いるのは請求額であり、アカウント名は不要である。Cloudflare のサブスクリプションには `client_secrets` 項目があり、名前から認証情報を含みうるため、値の有無にかかわらず除く。

#### Scenario: 取得成功時の保存

- **WHEN** ある提供元から応答を取得できた
- **THEN** 応答本文が対象日と取得元ごとに保存され、認証情報は含まれない

#### Scenario: 個人情報を含む応答の保存

- **WHEN** Cloudflare の従量課金の応答を保存する
- **THEN** 各行からアカウント名が除かれ、請求額など判定に用いた項目は残る

#### Scenario: 認証情報を含みうる項目の除去

- **WHEN** Cloudflare のサブスクリプションの応答を保存する
- **THEN** 各契約から `client_secrets` が除かれ、価格とプランなど判定に用いた項目は残る
