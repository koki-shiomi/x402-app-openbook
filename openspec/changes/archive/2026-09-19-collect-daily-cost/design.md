## Context

①`setup-openbook-foundation` の実装は完了し本番稼働中。`CollectionSource` インタフェース（`id` / `revisable` / `collect(date)` / `canCollect(date, now)`）が用意されており、本チェンジはこれを満たす 4 つの実装を追加して `SOURCES` へ登録する。バッチ・保存・集計・換算の既存コードは変更しない。動機は [proposal.md - Why](proposal.md) を参照。

設計を規定するのは、2026-09 に各 API を実測して確認した制約である。詳細は [openspec/config.yaml](../../config.yaml) に記録済みで、要点は次のとおり。

| 提供元 | 取得できるもの | 制約 |
| --- | --- | --- |
| Claude | 日次バケットの費用、モデル別内訳 | **単位はセント**、組織全体しか返らずキー単位で絞れない、Admin キーが必須で権限を絞れない |
| Cloudflare | サブスクリプション、従量課金、請求実績 | 従量課金は無料枠内の利用も請求額 0 の行で返す、1 リクエスト 90 日以内、各行にメールアドレスを含む、請求プロフィールが個人情報を返す |
| Resend | 日別送信数 | 課金額の API がない、遡及は約 30 日、プラン判定用ヘッダは送信時のみ、API キーは `full_access` が必須 |
| Supabase | 組織プラン、課金アドオン | 使用量の API がない |

## Goals / Non-Goals

**Goals:**

- 4 提供元すべてについて、日次の費用または「0 円である根拠」を記録する
- 実測値（Claude）と推定値（他 3 社）を、レコードだけから判別できる状態にする
- 取得できなかった提供元を 0 円と区別し、欠測として残す

**Non-Goals:**

- 収益の取得（③で実施）
- 過去分の遡及取り込み（本チェンジ稼働開始日以降を対象とする）
- ドメイン登録費の計上（アプリの運用費と性質が異なるため対象外）
- 無料枠超過時の能動的な通知（超過は算出根拠の変化として記録されるが、通知手段は運用開始後に判断する）

## Decisions

### 決定 1: Claude の費用はワークスペース単位で切り分ける

`cost_report` を `group_by[]=workspace_id` と `group_by[]=description` で呼び出し、sizet 専用ワークスペースの行のみを費用エントリにする。対象ワークスペース ID は設定値として持つ。

**理由:** `cost_report` は組織全体の費用を返し、API キー単位のフィルタや grouping を提供していない。分解できる軸はワークスペースと description のみである。Claude Code など他用途の利用が同じ組織にあるため、切り分けなければ公開する費用が過大になる。

**当面は Default ワークスペースを対象とする:** 現状 `sizet` キーは Default ワークスペースにあり、Claude Code のキーは別ワークスペースにあるため、Default を対象とすれば今日時点では正しく切り分けられる。専用ワークスペースの作成は推奨だが必須とはしない。

ただし Default は「何も指定しなかったキーが入る場所」であるため、今後 Default に別用途のキーを作った時点で、警告なく費用へ混入する。この運用を選ぶ条件として **Default に sizet 以外のキーを作らない**ことを前提に置く。混入が疑われる場合は、専用ワークスペースへ移行して対象を切り替える。

**設定漏れとの区別:** Default ワークスペースの `workspace_id` は応答上 `null` になる。設定値をそのまま `null` とすると「Default を意図して選んだ」のか「設定し忘れた」のかを区別できず、設定漏れのまま組織全体を計上する危険がある。設定値には `"default"` という明示的な指定を用い、実装側で `workspace_id === null` に対応付ける。

**検討した代替案:** `usage_report` の `api_key_ids[]` フィルタでトークン数を取得し、公開単価から算出する案（`derived`）。キー単位で確実に分けられるが、実測値ではなくなり、単価表の保守が必要になる。ワークスペース分離で実測値を保てるため採らない。

### 決定 2: セント単位の変換は境界で 1 回だけ行い、生応答を残す

`cost_report` の応答を受け取った直後に 100 で除して USD へ変換し、以降は USD として扱う。応答本文はそのまま `raw/` に保存する。

**理由:** 変換箇所が散ると 100 倍または 1/100 の誤りが混入する余地が増える。境界で 1 回に限定し、変換前の値を保存しておけば、公開値が誤っていた場合に後から検証できる。

**検証方法:** 同一期間の `usage_report` からトークン数を取得し、公開単価で計算した値と一致することをテストで確認する。実測では入力 10,071 トークン × $1/MTok = $0.010071 に対し応答は `1.0071` で、4 項目すべて一致した。この関係をテストに固定する。

### 決定 3: 0 円は「プランを確認した結果」として記録する

Cloudflare・Resend・Supabase の 0 円は、取得方式 `estimated`（月額 0 円の日割り）とし、算出根拠にその日 API で確認したプラン情報を含める。

**理由:** 設定ファイルに書いた月額から日割りするだけでは、実際に無料プランのままかどうかの裏付けがない。プランや課金対象の有無を毎日取得して根拠に残せば、「その日は課金対象がなかった」ことが公開データから追跡できる。

**提供元ごとの根拠:**

| 提供元 | 算出根拠に記録する内容 |
| --- | --- |
| Cloudflare | サブスクリプションの件数とプラン名（いずれも価格 0）、従量課金の行数と請求額の合計（0）、対象日の請求有無 |
| Supabase | 組織プラン名、プロジェクトごとの課金アドオン件数 |
| Resend | 設定で宣言したプラン名、対象日の送信数 |

Resend だけ API 由来の裏付けが弱い。プラン判定に使える `x-resend-daily-quota` ヘッダは送信時のレスポンスにしか付かず、費用確認のためにメールを送るのは目的に反する。送信数を併記することで、無料枠の上限に対する余裕は判断できる状態にする。

Cloudflare のサブスクリプションと従量課金は、件数ではなく金額で判定する。R2 を有効にすると価格 0 のサブスクリプション（R2 Paid）が作成され、従量課金は無料枠に含まれる利用も請求額 0 の行として返すため。判定はアカウント単位であり、OpenBook 自身の R2 利用も含まれる。価格と請求額は JSON の数値で返るため、10 進小数の文字列へ変換してから合計する。浮動小数点のまま加算すると、相殺して 0 になるはずの合計が 0 にならない場合がある。

### 決定 4: 遡及可能期間は収集ソース自身が宣言する

各収集ソースが `canCollect(date, now)` を実装し、提供元の遡及制限を表現する。①の月次クローズはこの判定を用いて再収集の可否を決める。

| 提供元 | 宣言する内容 |
| --- | --- |
| Resend | 実行時刻から 29 日以内の対象日のみ取得可能 |
| Cloudflare | 前日までのみ取得可能。過去日の再収集では既存値を維持する |
| Claude | 制限なし |
| Supabase | 当日のプラン状態しか取得できないため、過去日の再収集では既存値を維持する |

Cloudflare の従量課金の期間指定は終了日を含まないため、対象日 1 日分は対象日の翌日を終端として要求する。

**Resend を 29 日とする理由:** 実測では約 30 日を超える指定が切り詰められた。境界が正確に 30 日かは確認できていないため、切り詰めが起きない側へ 1 日の余裕を持たせる。切り詰められた値を対象日の値として記録すると、誤ったデータが公開される。

**Supabase と Cloudflare の扱い:** Supabase のプランと課金アドオン、Cloudflare のサブスクリプションは現在の状態しか返さず、過去の時点を指定する手段がない。当日分は現在の状態を根拠にできるが、過去日の再収集で現在の状態を適用すると、その日の実態と異なる判定になる。たとえば後から有料の契約を追加すると、無料だった過去日まで欠測に置き換わる。過去日については既存値を維持する。Cloudflare の従量課金と請求実績は過去日を指定できるが、3 点の判定を 1 つのエントリにまとめているため、ソース全体を前日までとする。

**引き継ぐ値がない場合:** 遡及可能期間外のソースは既存のレコードから値を引き継ぐが、既存のレコードに当該ソースの値がないこともある（本チェンジより前に作成されたレコードなど）。この場合は、遡及可能期間外のため取得できない旨を欠測として記録する。レコードからは「取得したが費用がなかった」と「取得していない」を区別できないため、遡及可能期間を宣言するソースは、取得に成功した場合に必ずエントリを返すものとする（Resend・Supabase・Cloudflare はいずれも 0 円のエントリを返す）。

### 決定 5: 収集ソースは提供元ごとに 1 ファイルへ分ける

`apps/api/src/sources/claude.ts` / `cloudflare.ts` / `resend.ts` / `supabase.ts` として実装し、`sources/index.ts` で登録する。

**理由:** 提供元ごとに API の形も制約も異なり、共通化できる部分がほとんどない。1 ファイルに集約すると、ある提供元の API 変更が他の提供元の実装に影響する余地が生まれる。②以降で提供元が増減する前提でも、ファイル単位で追加・削除できる形が扱いやすい。

### 決定 6: 認証情報は Worker のシークレットで渡し、未設定は欠測とする

4 つの認証情報を Worker のシークレットとして設定する。型は手書きの宣言で持ち、設定ファイルには値を置かない（①で `ADMIN_TOKEN` に用いた方式と同じ）。

**未設定時の挙動:** 認証情報がない提供元は収集を試みず、欠測として記録する。0 円として記録すると、「無料枠内で 0 円」と「そもそも取得していない」が公開データ上で区別できなくなる。

### 決定 7: 生応答から個人情報と認証情報を含みうる項目を除いてから保存する

Cloudflare の従量課金の応答は各行から `BillingAccountName` を、サブスクリプションの応答は各契約から `client_secrets` を取り除いてから `raw/` に保存する。

**理由:** `BillingAccountName` には請求先のメールアドレスを含むアカウント名が入る。費用の判定には請求額しか用いず、アカウント名は不要である。請求プロフィールを呼び出さない方針（[provider-credentials](specs/provider-credentials/spec.md)）と同じく、費用の確認に不要な個人情報をシステム内に持たない。`client_secrets` は確認時点では null だが、名前から認証情報を含みうるため、値の有無にかかわらず除く。生応答を公開するかは⑤で決めるが、保存時点で除いておけば公開範囲の判断に依存しない。

### 決定 8: 月次クローズは既存のレコードがある日だけを再収集する

①では月次クローズで前月の全日を再収集しており、レコードがない日には新たにレコードを作成していた。本チェンジから実データが入るため、そのままでは収集を開始する前の日（2026 年 9 月であれば 1〜7 日）を遡って取り込むことになる。遡及取り込みは行わない（Non-Goals）ため、当月中の再収集と同じく、既存のレコードがある日に限る。

**トレードオフ:** 稼働開始後に全ソースが失敗してレコードが作成されなかった日も、月次クローズでは埋まらない。その日は実行記録に失敗が残るため、手動再実行で埋める。

## Risks / Trade-offs

- **Default ワークスペースへの他用途キーの混入** → Default は指定なしのキーが入る場所であり、今後 sizet 以外のキーを作ると警告なく費用に混入する。混入しても API 上は区別できないため、公開値が過大になっても検知できない。専用ワークスペースへの移行が根本的な対策であり、当面は運用上の前提として扱う
- **対象ワークスペースの設定誤り** → 存在しないワークスペース ID を設定すると費用が常に 0 件になる。実データが入るはずの日に費用エントリが 0 件であることを、実装後の確認項目とする
- **セント変換の誤り** → 公開値が 100 倍または 1/100 になる。決定 2 のとおり変換を境界の 1 箇所に限定し、使用量レポートとの一致をテストで固定する。生応答を保存しているため事後検証も可能
- **Resend のプラン宣言が実態と乖離する** → 有料プランへ移行したのに設定を更新し忘れると、課金が発生しているのに 0 円を公開し続ける。算出根拠にプラン名を記録することで、公開データを見れば何を前提とした 0 円かは判別できる。API 由来の検知手段がない点は残る制約として受け入れる
- **Supabase と Cloudflare の過去日の根拠が現在の状態に依存する** → 決定 4 のとおり過去日は既存値を維持するため、収集を開始した日より前の日については根拠を持てない。稼働開始日以降を対象とする方針と整合する。当日分も、実行時点の状態を前日の根拠とするため、日付が変わってから実行までの間に契約が変わると前日の判定に反映される
- **Claude Admin キーの権限の広さ** → 権限を絞る手段が提供されていない。有効期限を設定し、他の認証情報とは扱いを分けて記録する。漏洩時の影響が最も大きい認証情報である
- **Cloudflare トークンの兼用** → 請求情報の読み取りに限定したトークンは発行できるが、運用上の判断で、Workers・R2 の編集権限を持つデプロイ用のトークンを Worker のシークレットにも置く。漏洩すると、Worker の書き換えと、R2 に保存したレコードの改変・削除が可能になる。ハッシュを刻印した月の改変は検証で検知できるが、刻印前の当月分は検知できない
- **Resend API キーの権限の広さ** → 読み取り専用の権限が提供されておらず、送信数の取得には `full_access` が必要である。漏洩すると、メール送信を含むすべてのリソースの作成・変更・削除が可能になる
- **公開する費用合計が請求実績と一致しない** → ドメイン登録費を対象外とするため。対象外である事実を利用者が知れる形で示す必要があり、⑥のフロントエンドでの表示方法にも影響する

## Migration Plan

1. 対象ワークスペースを設定する（当面は `"default"`）。専用ワークスペースへ移行する場合はそのワークスペース ID を設定する
2. 4 つの認証情報を Worker のシークレットとして設定する
3. 収集ソースを実装して `SOURCES` へ登録し、デプロイする
4. 手動再実行で対象日を指定し、4 提供元すべてのエントリが記録されることを確認する
5. Claude の費用が使用量レポートから算出した値と一致することを確認する

ロールバックは、`SOURCES` の登録を空に戻して再デプロイすることで行う。保存済みのレコードは不変であり削除しないため、誤ったデータを記録した場合は訂正リビジョンで上書きする。対象月がクローズされていなければ訂正できる。

## Open Questions
