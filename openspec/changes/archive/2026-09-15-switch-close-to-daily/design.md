## Context

①`setup-openbook-foundation` の決定 9 で、レコードに確定状態を持たせず、月次クローズを書き込みの締切とし、クローズ済みの月をハッシュ刻印の対象とした。②`collect-daily-cost` と③`collect-daily-revenue` は本番稼働中で、月次クローズは一度も実行していない（クローズ記録は存在しない）。

本チェンジは、この締切を廃止して刻印を日次に寄せる。動機と優先順位は [proposal.md - Why](proposal.md) を参照。

現在の実装で締切に関わる部分は次のとおり。

| 箇所 | 役割 |
| --- | --- |
| `storage.ts` の `closeKey` / `isMonthClosed` / `closeMonth` | クローズ記録の保存と、クローズ済み月への書き込み拒否 |
| `schedule.ts` の `runMonthlyClose` / `readClose` / `previousMonth` | 月次クローズの実行と記録 |
| `schedule.ts` の `recollectCurrentMonth` | 当月内の既存レコードの再収集 |
| `batch.ts` の `hasSameContent` | 内容が同一かの判定（生成時刻・訂正情報・為替の取得時刻を除外） |
| `index.ts` と `wrangler.jsonc` の `0 7 6 * *` | 月次クローズの定期実行 |

## Goals / Non-Goals

**Goals:**

- 前日分を収集した直後に刻印できる状態にする（刻印そのものは④）
- 提供元の調整によって過去の値が変わった場合、訂正リビジョンとして公開データに反映する
- 1 円未満の変動で刻印を繰り返さない
- 2026-10-06 の月次クローズが発火する前に本番へ反映する

**Non-Goals:**

- ハッシュ刻印の実装と検証手順（④で定める）
- 確定値の取得。AdMob は API から確定額を取得できない
- 締切に代わる別の凍結手段の導入

## Decisions

### 決定 1: 刻印を締切から切り離し、①の決定 9 を置き換える

刻印は「その時点の最新リビジョンの証明」とする。クローズ済み期間への書き込み拒否は廃止し、値が変われば訂正リビジョンを追加して刻印し直す。

**理由:** ①の決定 9 は「刻印後に値が変わる」状況を構造的に排除するために締切を置いた。しかし締切は同時に、提供元の調整を公開データへ反映する手段も封じる。公開の狙いは支払額への一致よりも、毎日取得している事実と改ざんされていない事実を早く示すことにあるため、後者を優先する。

**検証手順への影響:** 同じ日に複数のハッシュがチェーン上に並ぶ。④では「最新の刻印が現行の値、過去の刻印は訂正の履歴」と定める必要がある。①の決定 9 で代替案「取得のたびに刻印する」を退けた理由（どのリビジョンを見るべきかの判断が必要になる）は残るため、④はこの判断規則を仕様として明示する。

### 決定 2: 訂正リビジョンの追加を閾値で抑える

収益合計と費用合計の変化が、いずれも「差が 1 円以下、かつ既存の値に対する比率が 1% 以下」に収まり、かつ金額以外に違いがない場合は、訂正リビジョンを追加しない。

**判定の順序:**

1. 生成したレコードと既存の最新リビジョンを、生成時刻・訂正情報・為替の取得時刻を除いて比較する（現行の `hasSameContent`）。同一なら追加しない
2. 金額（`totals.revenueJpy` と `totals.costJpy`、および各エントリの金額）以外に違いがあれば追加する
3. 金額の違いのみの場合、収益合計と費用合計それぞれの差を評価し、両方が閾値以下なら追加しない

**理由:** 金額以外の違い（欠測の解消、エントリの増減、算出根拠の変化）は、額が動かなくても内容が変わったことを意味する。閾値で見送ると、公開データから変化そのものが消える。一方で金額は、AdMob の推定値が 0.01 円単位で揺れるため、そのたびに刻印し直す価値がない。

**比率の扱い:** 既存の値が 0 の場合、比率は定義できない。0 から値が現れることは「収益が発生した」という情報そのものなので、比率の条件を満たさないものとして扱い、常に訂正リビジョンを追加する。

**閾値の持ち方:** 共有パッケージの定数として持ち、変更はデプロイで反映する。環境変数にしないのは、閾値が変わると公開データのリビジョンの増え方が変わるため、コードとテストと同時に変更したいからである。

**代替案:** 閾値以下でも訂正リビジョンは追加し、刻印だけ見送る案。取得値をそのまま残せるが、最新リビジョンが未刻印になり、その差分については改ざんを検知できない。公開されている値が常に刻印済みである状態を優先して採らない。

### 決定 3: 再収集の対象を実行時点から 40 日以内とする

`recollectCurrentMonth` を、実行時点から 40 日以内の既存レコードを対象とする処理へ置き換える。日数は共有の定数とする。

**理由:** 当月内に限ると、月末の調整が翌月に反映された場合に取り込めない。40 日あれば、翌月初のどの日に実行しても前月の全日が対象に入る（例: 10-01 の実行で 08-22 まで遡る）。月の後半になると前月の古い日が対象から外れるが、その時点では調整が既に取り込まれている。

**呼び出し回数:** 1 回の日次実行で最大 40 日分を再収集する。Cloudflare と Supabase は前日までしか遡れないため呼び出さず既存値を引き継ぐ。Resend は 29 日以内のみ。Claude と AdMob は全日を呼ぶため、1 日あたり 3 回（Claude 1 回、AdMob 2 回）で最大 120 回程度になる。いずれの提供元も、この規模で制限に達する記述はない。

### 決定 4: 実行記録に、見送った変化と呼び出さなかった取得元を残す

実行記録へ次の 2 つを加える。

| 項目 | 内容 |
| --- | --- |
| 見送った変化 | 収益合計・費用合計の既存値と新しい値、差、判定に用いた閾値 |
| 呼び出さなかった取得元 | 遡及可能期間外と判定した収集ソースの識別子 |

**理由:** どちらも公開データには現れない。記録がなければ「値が動いていないのか、動いたが見送ったのか」を後から区別できない。呼び出さなかった取得元は、これまで月次クローズの記録に残していたため、クローズの廃止で失われる。

### 決定 5: クローズの機構を削除する

`closeKey` / `isMonthClosed` / `closeMonth` / `CloseRecord`、`runMonthlyClose` / `readClose`、月次の Cron（`0 7 6 * *`）、およびそれらのテストを削除する。

**理由:** 締切がなくなると、これらは判定する対象を持たない。残すと「クローズという状態があるが何も禁じない」という理解しにくい構造になる。

**保存済みデータ:** 本番にクローズ記録は存在しないため、移行や削除は不要である。

## Risks / Trade-offs

- **リビジョンが増え続ける余地** → 締切がないため、原理的には同じ日のリビジョンが際限なく増えうる。実際には再収集の対象が 40 日以内に限られ、閾値以下の変動は無視するため有界である。提供元の調整は月末で終わるため、1 日あたり数リビジョンに収まる見込み
- **閾値以下の差分が公開値に残らない** → 公開値は最大で 1 円（かつ 1%）ずれうる。実行記録に差分を残して追跡可能にする。刻印済みの値と公開値が一致する利点を優先する
- **同じ日に複数のハッシュが並ぶ** → 検証手順が「最新が現行、過去は履歴」という判断を伴う。④で規則を明示しないと、検証者がどのハッシュを見るべきか分からない
- **刻印回数の増加** → 日次 1 回に加えて訂正のたびに刻印する。Arc テストネットのため費用面の影響は小さいが、④の設計では失敗時の再試行を考慮する必要がある
- **9 月の締切** → 2026-10-06 07:00 UTC までに本番へ反映しなければ、9 月が恒久的に締まり、本チェンジの方針を 9 月へ適用できない

## Migration Plan

1. 閾値と再収集の日数を共有パッケージの定数として定義する
2. 訂正リビジョンの判定、再収集の対象期間、実行記録の拡張を実装する
3. クローズの機構と月次の Cron を削除する
4. 本番へデプロイし、日次実行で前日のレコードが記録され、既存日の再収集で不要なリビジョンが増えないことを確認する
5. ①のタスク 6.5（月次クローズの本番実行）を対象外として扱い、関連するメモリを更新する

ロールバックは、デプロイを直前のバージョンへ戻すことで行う。保存済みのレコードは不変であり、本チェンジで削除するオブジェクトもないため、データ面の影響はない。ただし戻した時点で月次クローズの Cron が復活するため、2026-10-06 を過ぎている場合は 9 月が締まる点に注意する。
