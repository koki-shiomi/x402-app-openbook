## Why

2026-09-16 の日次実行が Cloudflare Workers のサブリクエスト上限に達し、収集の途中で AdMob が「Too many subrequests」で失敗した。これが提供元の欠測として公開レコードに記録され、実体のない訂正リビジョンまで生んだ。同じ実行の最後段にある刻印も最初の RPC で失敗し、当該日は未刻印のまま残って、有料 API がその日を拒み続けている。

再収集の対象は保存済みのレコードが増えるほど伸びるため、放置すれば毎日悪化する。40 日分が揃った定常状態では 1 回の実行で約 164 件の外部呼び出しとなり、上限の 50 件を大きく超える。

## What Changes

- 日次実行を複数の定期実行へ分割し、1 回の実行が扱う対象日の範囲を限定する
- 刻印を収集とは別の定期実行へ移す。手動再実行の後段で刻印する動作は変えない
- 過去日の再収集で為替レートを取得し直さず、保存済みのレコードが記録しているレートを再利用する
- 前日を 1 回の実行で二重に収集している重複を解消する
- **BREAKING**: 自分の資源制約による失敗を提供元の欠測として記録しない。これまで `incomplete` に現れていた種類の失敗の一部が、今後は実行記録にのみ現れる

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `daily-batch`: 日次の定期実行を複数の実行へ分割する。過去日の再収集は 1 回の実行で全期間を扱わず、実行ごとに定めた範囲を扱う。資源制約による失敗を提供元の欠測と区別する
- `hash-anchoring`: 刻印の契機を「収集を行った実行の後段」から「収集とは独立した実行」へ改める
- `currency-conversion`: 過去日の再収集では、保存済みのレコードが記録しているレートを再利用する

## Impact

- `apps/api/src/index.ts`: `scheduled` が起動した定期実行を判別し、担当する処理だけを行う
- `apps/api/src/schedule.ts`: 再収集の対象日の算出が範囲を受け取る。前日の二重収集の解消
- `apps/api/src/batch.ts`: 為替レートの再利用と、資源制約による失敗の扱い
- `apps/api/wrangler.jsonc`: 定期実行の定義が 1 本から 4 本になる
- 公開されるレコードの `incomplete`: 資源制約による失敗が現れなくなる
- 運用: 前日分が刻印されるまでの時間が延び、有料 API が当該日を拒む時間帯が長くなる
