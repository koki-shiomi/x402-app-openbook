## Purpose

公開された日次レコードのバイト列が、チェーン上の刻印と照らして現行の値か、訂正の履歴か、未刻印か、改ざんされたものかを判定する規則と手段を定める。同じ日に複数の刻印が並んでも、検証者が迷わず同じ結論に達するようにする。

## ADDED Requirements

### Requirement: 判定の分類と規則

システムは、日次レコードのバイト列を検証した結果を、次の 4 つのいずれかに分類しなければならない（SHALL）。判定には、バイト列から算出した SHA-256 と、バイト列が示す対象日・リビジョン番号で照会したチェーン上の値を用いる。

| 分類 | 条件 | 意味 |
| --- | --- | --- |
| 現行 | 刻印されたハッシュが算出値と一致し、リビジョン番号がその対象日の最大のリビジョンと等しい | その対象日の現在の値として刻印されている |
| 履歴 | 刻印されたハッシュが算出値と一致し、リビジョン番号がその対象日の最大のリビジョンより小さい | 刻印後に訂正された、過去の値である |
| 未刻印 | そのリビジョンに刻印がない | 刻印による証明がない |
| 不一致 | そのリビジョンに刻印があり、算出値と一致しない | 刻印後にバイト列が変わっている |

同じ対象日に複数の刻印がある場合、最大のリビジョンの刻印を現行の値としなければならない（SHALL）。刻印の時刻や記録の発行順で現行の値を決めてはならない（MUST NOT）。

リビジョン番号はコントラクトが単調増加を保証するため、時刻に依存しない一意の規則として用いる。

#### Scenario: 現行の値

- **WHEN** リビジョン 2 まで刻印された対象日の、リビジョン 2 のバイト列を検証する
- **THEN** 「現行」と判定される

#### Scenario: 訂正の履歴

- **WHEN** リビジョン 2 まで刻印された対象日の、刻印済みのリビジョン 1 のバイト列を検証する
- **THEN** 「履歴」と判定される

#### Scenario: 未刻印のリビジョン

- **WHEN** 刻印されていないリビジョンのバイト列を検証する
- **THEN** 「未刻印」と判定される

#### Scenario: 書き換えられたバイト列

- **WHEN** 刻印済みのリビジョンのバイト列を 1 バイトでも変えて検証する
- **THEN** 「不一致」と判定される

### Requirement: 判定に用いる情報の限定

判定は、検証するバイト列とチェーン上の値だけで行わなければならない（SHALL）。運営者が保存する刻印の結果や API の応答を判定の根拠にしてはならない（MUST NOT）。

運営者の記録を根拠にすると、運営者が記録ごと書き換えた場合に改ざんを検知できないためである。

#### Scenario: 運営者の記録がない状態での検証

- **WHEN** 運営者の刻印の結果を参照できない環境で、刻印済みのリビジョンのバイト列を検証する
- **THEN** 運営者の記録を参照できる場合と同じ分類になる

### Requirement: 検証関数

システムは、日次レコードのバイト列を受け取り、分類と判定の根拠を返す検証関数を提供しなければならない（SHALL）。根拠には、算出したハッシュ、チェーン上に刻印されたハッシュ、対象日の最大のリビジョン、照会したコントラクトのアドレスとチェーン ID を含めなければならない（SHALL）。

検証関数は、受け取ったバイト列をそのままハッシュの算出に用いなければならない（SHALL）。解析して直列化し直したバイト列を用いてはならない（MUST NOT）。

検証関数は、ブラウザと Cloudflare Workers の両方で動作しなければならない（SHALL）。⑥の公開ダッシュボードでも同じ判定を用いるためである。

#### Scenario: 判定の根拠の返却

- **WHEN** 刻印済みのリビジョンのバイト列を検証関数に渡す
- **THEN** 分類とともに、算出したハッシュ・刻印されたハッシュ・最大のリビジョン・コントラクトのアドレス・チェーン ID が返る

#### Scenario: 空白の違いを含むバイト列

- **WHEN** 刻印済みのリビジョンと同じ内容で、JSON の空白だけが異なるバイト列を検証関数に渡す
- **THEN** 「不一致」と判定される

### Requirement: 検証できないバイト列

バイト列が日次レコードとして解析できない場合、または対象日かリビジョン番号を読み取れない場合、検証関数は分類を返さず、検証できない理由を返さなければならない（SHALL）。

照会する対象日とリビジョンが定まらないまま「未刻印」と判定すると、不正な入力を刻印の欠落と誤認させるためである。

#### Scenario: JSON として解析できないバイト列

- **WHEN** JSON として解析できないバイト列を検証関数に渡す
- **THEN** 分類は返らず、解析できない旨の理由が返る

#### Scenario: 対象日を持たないバイト列

- **WHEN** 対象日の項目を持たない JSON のバイト列を検証関数に渡す
- **THEN** 分類は返らず、対象日を読み取れない旨の理由が返る

### Requirement: 検証手順書

システムは、第三者が本システムのコードを実行せずに、エクスプローラと SHA-256 を算出する一般的な道具だけで分類に到達できる検証手順書を提供しなければならない（SHALL）。手順書には、コントラクトのアドレス、チェーン ID、対象日の整数での表し方、算出したハッシュとチェーン上の値の表記の違い、4 つの分類の判定方法を含めなければならない（SHALL）。

コードの実行を前提にすると、検証者は本システムのコードそのものを信頼する必要が生じるためである。

#### Scenario: 手順書に従った検証

- **WHEN** 検証者が、刻印済みのリビジョンのバイト列を手順書だけに従って検証する
- **THEN** 検証関数と同じ分類に到達する
