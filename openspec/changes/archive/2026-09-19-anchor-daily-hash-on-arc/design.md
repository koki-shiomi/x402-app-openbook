## Context

日次レコードは R2 の `records/{date}/{NNN}.json` に正準 JSON のバイト列として保存され、訂正はリビジョンの追加で行う。`switch-close-to-daily` により書き込みの締切はなく、日次実行（06:00 UTC）は前日分の収集と、実行時点から 40 日以内の既存レコードの再収集を行う。手動再実行は任意の日を収集する。動機は [proposal.md - Why](proposal.md) を参照。

設計を規定する Arc テストネットの制約は次のとおり。2026-09-14 の実測と公式ドキュメントの確認結果は [openspec/config.yaml](../../config.yaml) に記録している。

| 項目 | 内容 |
| --- | --- |
| ガス | ネイティブの USDC で払う（18 桁）。`maxFeePerGas` が 20 Gwei 未満だとエラーなく破棄されうる |
| ファイナリティ | 1 秒未満、reorg なし。受領が得られれば確定とみなせる |
| ブロック間隔 | 約 0.5 秒（1 日あたり約 17 万ブロック） |
| `eth_getLogs` | 20,000 ブロックは取得でき、50,000 ブロックでは範囲超過になる |
| Workers の Cron | 実時間の上限は 15 分。ネットワーク待ちは CPU 時間に数えない |

## Goals / Non-Goals

**Goals:**

- 刻印の書き込み・照会・検証が、同じハッシュの算出と同じ照会の実装を共有する
- 刻印が一時的に失敗しても、手作業なしで次の実行が取りこぼしを解消する
- 検証者がイベントの走査なしに、チェーンへの照会 2 回で判定できる

**Non-Goals:**

- メインネットへの刻印と、テストネットから移行する手順
- 刻印の有無を公開物に添えること（⑤で行う）
- 検証の画面（⑥で行う）
- 残高不足や不一致の能動的な通知。実行記録に残すのみとする

## Decisions

### 決定 1: 刻印をコントラクトのストレージとイベントの両方に残す

コントラクトは、`(対象日, リビジョン) → ハッシュ` と `対象日 → 最大のリビジョン` をストレージに保持し、刻印ごとにイベントを発行する。照会は view 関数で行う。

**理由:** 検証者が必要とするのは「このリビジョンのハッシュ」と「この日の最大のリビジョン」の 2 つで、ストレージに持てば `eth_call` 2 回で済む。イベントだけで持つと、公式 RPC の取得範囲（20,000 ブロック ≒ 約 3 時間）ごとに稼働開始から走査する必要があり、1 年で約 3,000 回の呼び出しになる。イベントは、エクスプローラで訂正の履歴を時系列で読むために併せて発行する。

**単調増加の強制:** `revision > 最大のリビジョン` を満たさない刻印は拒否する。これにより上書きの禁止（同じリビジョンへの再書き込み）も同じ条件で成立し、「最大のリビジョンが現行」という検証の規則をコントラクト自身が保証する。

**検討した代替案:**

- コントラクトを持たず、トランザクションのデータ部にハッシュを載せる案。ガスは最小だが、書き込み主体の限定や単調増加をチェーン上で保証できず、検証者が送信元アドレスとトランザクションの並びを自分で解釈する必要がある
- イベントのみを発行する案。ガスは安いが、上記のとおり照会の回数が稼働期間に比例する

### 決定 2: 対象日は `uint32` の `YYYYMMDD`、ハッシュは SHA-256

| 項目 | 型 | 例 |
| --- | --- | --- |
| 対象日 | `uint32` | `20260913` |
| リビジョン | `uint32` | `2` |
| ハッシュ | `bytes32` | SHA-256 の 32 バイト |

**対象日:** ArcScan の Read Contract 画面に人が入力しやすく、表示を読んでそのまま日付と分かる。UNIX 日数（`20709` など）は変換が必要になり、文字列の `bytes32` は入力時の符号化を誤りやすい。

**ハッシュ:** `sha256sum`、ブラウザと Workers の Web Crypto、Node の `crypto` で算出でき、検証者に EVM 固有の道具を求めない。keccak256 はチェーン上で算出する場合に有利だが、本コントラクトはハッシュを受け取って保存するだけでチェーン上では算出しない。

**スキーマバージョン:** [financial-record](../../specs/financial-record/spec.md) は刻印にスキーマバージョンの併記を求めている。バージョンはレコードのバイト列に含まれ、ハッシュがそれを覆うため、コントラクトに別途持たない。

### 決定 3: 書き込み主体は 1 段階で変更できる

書き込み主体はデプロイ時の送信者とし、現在の書き込み主体が 1 回の呼び出しで別アドレスへ変更できる。

**理由:** 署名鍵を交換してもコントラクトのアドレスが変わらず、検証手順書と⑥の設定を更新せずに済む。変更しても既存の刻印は書き換えられないため、改ざんの余地は増えない。

**検討した代替案:** 受け手の承認を要する 2 段階の変更。アドレスの誤入力で書き込み不能になる事態を防げるが、利用者は運営者 1 名で変更の頻度も低い。誤った場合は新しいコントラクトを配備して移行できるため、構造の単純さを優先する。

### 決定 4: 刻印の対象は R2 の一覧の差分から求める

刻印の結果を `anchors/{date}/{NNN}.json`（`NNN` はリビジョン）に保存する。刻印の対象は、`records/` の一覧から各日の最新リビジョンを求め、対応する `anchors/` のキーがないものとする。

**理由:** R2 の一覧 2 回（ページ送りを含む）で全期間の対象が決まり、再収集の対象期間や過去の失敗の有無に依存しない。稼働 1 年でもキーは千件程度で、一覧の 1 ページに収まる規模である。

**チェーンを正とする扱い:** `anchors/` は対象の絞り込みと⑤への提供のための記録であり、正はチェーン上の値とする。送信前に各対象をチェーンへ照会し、[hash-anchoring](specs/hash-anchoring/spec.md) の「送信前のチェーンとの突き合わせ」の表に従って扱う。照会はマルチコール（Arc テストネットに Multicall3 が配備済み）で 1 回にまとめる。

**検討した代替案:**

- 全日をチェーンへ照会して未刻印を求める案。R2 に記録を持たずに済むが、⑤がトランザクションのハッシュを添えられない
- 収集の実行記録から「リビジョンを追加した日」を拾う案。刻印が失敗した日や、刻印の導入前のレコードを取りこぼす

### 決定 5: 1 件のトランザクションに含める対象は 30 件まで

**理由:** 刻印の導入時点で、稼働開始（2026-09-08）以降の全日を 1 回で刻印できる数とする。導入が 10 月上旬であれば対象は 25 日前後になる。1 件あたりのガスはストレージ 2 スロットの書き込みとイベント 1 件で数万程度と見込むが、ブロックのガス上限は公式ドキュメントに記載がないため、配備時に実測して定数を調整する（Open Questions）。

超えた分は次の実行に回り、新しい対象日から含める（[hash-anchoring](specs/hash-anchoring/spec.md)）。

### 決定 6: 送信は viem で行い、受領の待機に上限を設ける

Worker から viem の `privateKeyToAccount` で署名し、`arcTestnet` のチェーン定義に、シークレットで与えた RPC の URL を組み合わせて送信する。`maxFeePerGas` は見積もり値と 20 Gwei の大きいほうとする。送信後は受領を最大 60 秒待つ。

**RPC の URL をシークレットにする理由:** 公式ドキュメントの URL（`rpc.testnet.arc.io`）と viem の既定（`rpc.testnet.arc.network`）が異なり、現時点では両方応答する。ドメインの移行が進んだ場合に、デプロイせずに切り替えられるようにする。

**受領の待機がタイムアウトした場合:** 失敗として実行記録に残し、`anchors/` には保存しない。トランザクションが後から成立していた場合は、次の実行の突き合わせで「刻印済みで一致」と判定され、トランザクションのハッシュを持たない結果として記録される。

**検討した代替案:** ethers.js。機能は同等だが、viem は Arc テストネットのチェーン定義を同梱しており、Workers での利用例も多い。検証関数を共有パッケージに置く都合上、依存を 1 つにまとめる。

### 決定 7: 刻印は収集の後段で同じ関数を呼ぶ

日次実行は「前日分の収集 → 過去日の再収集 → 刻印」の順に行う。手動再実行は「指定日の収集 → 刻印」の順に行う。どちらも同じ刻印の関数を呼ぶ。手動再実行の応答には刻印の結果（成否とトランザクションのハッシュ）を加える。

刻印の関数は例外を外へ投げず、結果を実行記録に残して返す。収集の結果とは独立しており、刻印の失敗が日次実行や手動再実行の失敗にならない。

**刻印の実行記録:** `anchor-runs/{実行時刻}.json`（時刻は `2026-09-14T06-00-52Z` の形式）に保存する。収集の実行記録（`runs/{date}.json`）は対象日ごとに上書きするが、刻印は対象日をまたぐため実行ごとに別のキーとする。

### 決定 8: 設定と署名鍵はすべて Worker のシークレットで渡す

| 名前 | 内容 |
| --- | --- |
| `ARC_SIGNER_PRIVATE_KEY` | 刻印専用の EOA の秘密鍵 |
| `ARC_RPC_URL` | RPC の URL |
| `ARC_ANCHOR_CONTRACT` | コントラクトのアドレス |

チェーン ID はコードの定数（`5042002`）とし、RPC から得たチェーン ID と一致しない場合は送信しない。誤った RPC を設定して別のチェーンに刻印することを防ぐ。

秘匿不要なアドレスや URL もシークレットに寄せるのは、②の決定 6 と同じく設定箇所を 1 つにするためである。いずれかが未設定の場合は、刻印を行わず未設定の項目名を実行記録に残す。

### 決定 9: コントラクトは Arc Foundry で開発・配備・検証する

`contracts/` に Foundry のプロジェクトを置き、pnpm のワークスペースには含めない。コントラクトのテストは Solidity で書き、`arc-forge test` で実行する。配備は `arc-forge create`、ソースの検証は ArcScan（Blockscout）へ `arc-forge verify-contract` で行う。

**理由:** 公式チュートリアルが案内する手順であり、ソースを ArcScan で検証済みにすると、第三者がコントラクトの振る舞いを読んで確かめられる。

**ABI の共有:** 共有パッケージに ABI を定数として置き、刻印と検証の両方が参照する。ビルド結果の ABI（`arc-forge inspect`）との一致をタスクで確認する。

**検討した代替案:** npm の `solc` でコンパイルし viem で配備する案。ツールチェーンを pnpm に揃えられるが、コントラクトのテストを TypeScript からローカルの EVM に対して書く仕組みが別途必要になり、ソースの検証も手作業になる。

### 決定 10: 検証関数は共有パッケージに置き、全体の検証は行わない

`packages/shared` に、SHA-256 の算出、チェーンの照会、分類の判定を置く。刻印の関数も同じ算出と照会を使う。SHA-256 は Web Crypto（`crypto.subtle.digest`）で算出し、ブラウザ・Workers・Node 20 以降で同じ実装が動く。

検証関数はバイト列から対象日とリビジョン番号だけを読み取り、レコード全体の妥当性検証（`validateRecord`）はかけない。改ざんされたバイト列が妥当性検証で弾かれると、「不一致」ではなく「検証できない」と判定されてしまい、改ざんの検知という目的に反するためである。

**チェーンの照会の差し替え:** 照会は「ハッシュの照会」「最大のリビジョンの照会」を持つインタフェースとして受け取る。本番では viem の実装を渡し、テストではメモリ上の実装を渡す。

### 決定 11: 検証手順書は `docs/verify-anchor.md` に置く

手順は次の流れとする。記載する内容は [anchor-verification](specs/anchor-verification/spec.md) の「検証手順書」を参照。

1. レコードのバイト列を入手し、`sha256sum` でハッシュを算出する
2. バイト列の `date` と `revision` を読み、対象日を `YYYYMMDD` の整数に直す
3. ArcScan でコントラクトを開き、Read Contract でハッシュと最大のリビジョンを照会する
4. `sha256sum` の出力（`0x` なし）と照会結果（`0x` つき）を比べ、分類の表に当てはめる

## Risks / Trade-offs

- **[公開中の最新リビジョンが未刻印の時間がある]** → 保存から刻印までは同じ実行内の数秒だが、刻印が失敗すると次の実行まで未刻印になる。手動再実行で追加したリビジョンも同様である。`switch-close-to-daily` の proposal は「公開されている最新リビジョンは常に刻印済み」としているが、厳密には成り立たない。⑤で刻印の有無を公開物に添え、未刻印であることを隠さない
- **[署名鍵の漏洩]** → 攻撃者が存在しない大きいリビジョンを刻印すると、本物の最新リビジョンが「履歴」と判定される。刻印の前の突き合わせで「チェーンの最大のリビジョンが保存物より大きい」ことを不一致として実行記録に残す。発覚したら書き込み主体を新しい鍵へ変更する。偽の刻印は消せないため、手順書に「最大のリビジョンのバイト列が公開されていない場合は運営者に照会する」ことを記す
- **[テストネットの消去]** → 公式ドキュメントに継続性の記載がない。消去されると刻印の履歴を失い、R2 の `anchors/` だけが残る。メインネットへの移行は本チェンジの範囲外とする
- **[手数料の残高不足]** → 刻印が失敗し続け、未刻印の日が増える。失敗の理由は実行記録に残り、残高が戻れば次の実行で 30 件ずつ解消する。Faucet の配布量は [要確認]
- **[日次実行と手動再実行の同時実行]** → 同じ対象を 2 件のトランザクションで送り、後着が拒否される。拒否は実行記録に残り、次の実行の突き合わせで解消する。利用者が運営者 1 名のため、排他制御は設けない
- **[中間のリビジョンが刻印されない]** → 刻印までに複数回訂正された日は、途中のリビジョンがチェーンに残らない。途中の値は R2 に残り「未刻印」と判定される。刻印の目的は公開中の値の証明であり、訂正ごとに刻印するとトランザクションが実行の回数を超えて増える
- **[ABI の食い違い]** → 共有パッケージの ABI とコントラクトがずれると、刻印は拒否され、検証は誤った値を読む。ビルド結果との一致をタスクで確認し、コントラクトを変更したら同時に更新する

## Migration Plan

1. Arc Foundry を導入し、刻印専用の鍵を生成して Faucet からテストネット USDC を入れる
2. コントラクトのテストを通し、Arc テストネットへ配備して ArcScan でソースを検証する
3. 3 つのシークレットを Worker に設定する
4. Worker をデプロイする
5. 手動再実行で前日を指定し、2026-09-08 以降の全日の最新リビジョンが 1 件のトランザクションで刻印されることを確認する
6. 検証関数と検証手順書の両方で、刻印済みのリビジョンが「現行」と判定されることを確認する
7. 翌日の日次実行で、新しい前日分が刻印されることを確認する

ロールバックは Worker を直前のバージョンへ戻すことで行う。チェーン上の刻印と R2 の `anchors/` は消えないが、刻印が止まるだけで収集には影響しない。再開すると未刻印の日が次の実行で解消される。

## Open Questions

- **1 件のトランザクションに含める対象の上限（30 件）の妥当性:** 1 件あたりのガスとブロックのガス上限を、配備時にテストネットで実測して定数を調整する。上限の値が変わっても仕様と手順は変わらない
