## Context

3 件の詳細は proposal.md の「Why」を参照。

`apps/api/src/r2-listing.ts` には、接頭辞配下の全キーを `cursor` を辿って列挙する `listKeys` がすでにあるが、モジュール内に閉じている。`readCollectionRuns`（`runlog.ts`）と `listPaymentReceipts`（`payment/receipts.ts`）はそれぞれ `bucket.list()` を 1 回呼ぶだけで、続きを辿っていない。

`apps/web/src/app.ts` の接続の処理は、`connectWallet` → `ensureChain` → `connect.remove()` → `renderDepositPanel` の順で、最後の `renderDepositPanel` が残高を RPC で照会する。全体が 1 つの `try` に入っており、どこで失敗しても同じ文言を出す。

`scripts/check-crons.mjs` は `wrangler.jsonc` の `triggers.crons` と `src/triggers.ts` の定期実行の指定を突き合わせる。担当範囲はコメントにしか書かれておらず、比較の対象になっていない。

## Goals / Non-Goals

**Goals:**

- 列挙の辿り方を 1 箇所に集約し、同じ誤りが再発しないようにする
- 接続後の失敗を、接続の失敗と区別して示し、やり直せるようにする
- 担当範囲の記述のずれを、人手のレビューに頼らず検出する

**Non-Goals:**

- 実行記録の保存形式や保持期間の見直し
- 接続まわりの画面構成の作り直し

## Decisions

### 決定 1: キーの列挙を共通の処理として公開する

`r2-listing.ts` の `listKeys` を公開し、`readCollectionRuns` と `listPaymentReceipts` がこれを使う。`bucket.list()` を直接呼ぶ箇所をなくす。

同じ辿り方を 3 箇所で書き直すと、また 1 箇所だけ抜ける。現に `latestRevisionByPrefix` だけが正しく、他の 2 箇所が抜けていた。

**代替案:**

- それぞれの関数で個別に `cursor` を辿る。実装が重複し、次に追加する読み出しでも同じ抜けが起きうる

### 決定 2: 接続を取り除くのは、後続の処理が終わってからにする

`connect.remove()` を `renderDepositPanel` の後へ移す。あわせて、接続そのものの失敗と、接続後の失敗を別の `try` で扱い、後者では実際の失敗の内容を示す。

接続の操作は、やり直す手段そのものである。後続の処理が成功したことを確かめる前に取り除くと、失敗したときに何も残らない。

**代替案:**

- 失敗時に接続の操作を作り直す。取り除かなければ作り直す必要もない

### 決定 3: 担当範囲を設定ファイルのコメントから検査する

`wrangler.jsonc` のコメントに書かれた担当範囲を `check-crons.mjs` が読み取り、`COLLECTION_TRIGGERS` の `slice` と突き合わせる。一致しなければ失敗させる。

コメントは人が読む唯一の説明であり、実装とずれると誤った前提で判断することになる。定期実行の指定はすでに機械的に突き合わせているため、同じ仕組みに乗せる。

**代替案:**

- コメントから担当範囲の記述を削り、`src/triggers.ts` だけを唯一の出どころとする。設定ファイルだけを見たときに、4 本の定期実行が何を担当するのか分からなくなる
- 人手のレビューに任せる。今回それで見落とした

## Risks / Trade-offs

- **コメントの形式に依存した検査になる** → 形式が変われば検査は失敗する。黙って通り抜けるより、失敗して気づけるほうがよい
- **列挙を最後まで辿ると、記録が増えたときに読み出しが遅くなる** → 記録を一部しか返さないより正しい。実行記録を読むのは運用時の確認であり、利用者の要求の経路にはない

## Migration Plan

デプロイのみで完結する。保存物の移行はない。反映後は、実行記録の読み出しと画面の接続が従来どおり動くことを確認する。
