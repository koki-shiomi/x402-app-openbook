## Why

②`collect-daily-cost` で費用の実データを記録し始めたが、収益の取得元がないため、公開する収支は常に収益 0 円・赤字として表示される。本チェンジで sizet の収益源である AdMob 広告の収益を記録し、収支の両側をそろえる。

期限がある。2026-10-06 07:00 UTC の月次クローズで 9 月への書き込みが締め切られ、以降は 9 月の収益を追加できない。それまでに本番へデプロイする必要がある。

## What Changes

- **AdMob の推定収益を日次で取得し、収益エントリとして記録する**。AdMob API が返すのは推定収益のみで確定額を取得する手段がないため、取得方式は `measured`、改訂可能性は真とする
- **広告フォーマット別にエントリを分ける**。sizet はバナーとインタースティシャルを使っており、どの広告が収益を生んでいるかを公開データから読めるようにする
- **sizet のアプリの収益のみを対象とする**。AdMob アカウントに他のアプリが加わっても混入しないよう、アプリ ID で絞り込む
- **AdMob の集計タイムゾーンをエントリに記録する**。AdMob はアカウントのレポートタイムゾーンで日を区切り、レコードの対象日（UTC 暦日）と境界がずれるため
- **稼働開始日（2026-09-08）以降の 9 月分も記録する**。デプロイ後の当月中の再収集により、既存のレコードがある日へ収益が追加される。レコードがない 9 月 1〜7 日は対象外のまま
- **AdMob の認証情報は OAuth 2.0 のリフレッシュトークンで保持する**。AdMob API はサービスアカウントに対応していない。スコープは収益レポートに限定した `admob.report` とし、OAuth 同意画面を本番公開にする（テスト状態のまま発行したリフレッシュトークンは 7 日で失効する）

## Capabilities

### New Capabilities

- `revenue-collection`: AdMob から日次の収益を取得し、取得方式・改訂可能性・集計タイムゾーンつきの収益エントリへ変換する規則

### Modified Capabilities

- `provider-credentials`（②で新設、未アーカイブ）: AdMob の認証情報に求める権限と、リフレッシュトークンを失効させないための条件を追加する
- `daily-batch`: 当月中の再収集の対象が既存のレコードがある日に限られることを明示する。現在の実装の挙動であり、9 月 1〜7 日へ収益のためにレコードを作らないことの根拠になる

## Impact

- **コード**: `apps/api/src/sources/admob.ts` を追加し、`sources/index.ts` の収集ソースへ登録する。設定値の読み取り（`sources/config.ts`）とシークレットの型（`secrets.d.ts`）に AdMob の項目を加える。バッチ・保存・集計・換算の既存コードは変更しない
- **認証情報**: OAuth クライアント ID・クライアントシークレット・リフレッシュトークンの 3 つをシークレットとして、パブリッシャー ID とアプリ ID を設定値として Worker に設定する
- **事前作業**: Google Cloud プロジェクトで AdMob API を有効化し、OAuth 同意画面の作成と本番公開、OAuth クライアントの作成、リフレッシュトークンの発行を行う必要がある
- **公開データ**: 日次レコードの `revenues` に実データが入る。デプロイ後の再収集で、2026-09-08 以降の各日に訂正リビジョンが追加される
- **後続チェンジへの制約**: 9 月のクローズ時点で収益がそろい、④のハッシュ刻印の対象になる最初の月が費用と収益の両方を持つ
