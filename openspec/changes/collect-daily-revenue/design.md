## Context

①`setup-openbook-foundation` の基盤と②`collect-daily-cost` の収集ソースが本番稼働中である。本チェンジは `CollectionSource`（`id` / `revisable` / `collect(date)` / `canCollect(date, now)`）を満たす AdMob の収集ソースを 1 つ追加する。当月中の再収集・月次クローズ・遡及範囲外の値の引き継ぎ・部分失敗の扱いは既存の仕組みをそのまま使う。動機と期限は [proposal.md - Why](proposal.md) を参照。

設計を規定する AdMob API の制約は次のとおり。2026-09 の実測結果は [openspec/config.yaml](../../config.yaml) に、公式ドキュメントで確認した事実は各決定に記す。

| 項目 | 内容 |
| --- | --- |
| 取得できる収益 | `ESTIMATED_EARNINGS`（推定収益）のみ。マイクロ単位の整数で返る |
| 集計の区切り | アカウントのレポートタイムゾーン（sizet のアカウントは `Asia/Tokyo`）。上書きできるのは `America/Los_Angeles` のみ |
| 通貨 | 指定しなければアカウントの通貨（sizet のアカウントは `JPY`）。任意の通貨を指定すると Google が換算した値を返す |
| 認証 | OAuth 2.0 のみ。サービスアカウントは非対応 |
| スコープ | `admob.report`（レポートとアカウントの基本情報）と `admob.readonly`（全データ）の 2 種類 |

sizet は iOS の 1 アプリで、AdMob ネットワークのバナーとインタースティシャルを 1 ユニットずつ使う。メディエーションは使っていない。

## Goals / Non-Goals

**Goals:**

- 対象日の AdMob 推定収益を、広告フォーマット別・集計タイムゾーンつきで記録する
- AdMob の認証情報を、失効しにくく権限の狭い形で保持する
- 2026-10-06 の 9 月クローズまでに本番へデプロイする

**Non-Goals:**

- 確定額（AdMob 管理画面の Transactions）の取得。API が提供していない
- メディエーション経由の収益。sizet は使っていない
- 国別・広告ユニット別の内訳
- トークン失効時の能動的な通知。失効は欠測と実行記録の理由として現れる

## Decisions

### 決定 1: ネットワークレポートを 1 日 1 回、アプリで絞り込んで取得する

`accounts.networkReport.generate` を、期間を対象日 1 日、ディメンションを `DATE` と `FORMAT`、指標を `ESTIMATED_EARNINGS` として呼び出す。`APP` ディメンションのフィルタ（`matchesAny`）で sizet のアプリ ID に絞り込む。`timeZone` と `localizationSettings` は指定しない。

応答はヘッダ・行・フッタの 3 種類のメッセージを並べた配列で、行ごとに `FORMAT` の値と `ESTIMATED_EARNINGS` の `microsValue` を持つ。1 行を 1 件の収益エントリにする。要求した指標がすべて 0 の行は返らないため、収益が 0 の日は行がなく、エントリも作らない（[revenue-collection](specs/revenue-collection/spec.md) の「広告の配信がなかった日の取得」）。

**検討した代替案:** 月全体を 1 回で取得して日ごとに配る案。呼び出し回数は減るが、`CollectionSource` は対象日ごとに呼ばれる設計であり、1 日分の取得に収まらない仕組みを持ち込むことになる。当月中の再収集でも 1 日あたり 2 回（アカウント情報と収益）の呼び出しで済むため採らない。

### 決定 2: タイムゾーンと通貨はアカウント情報から毎回取得する

収益の取得前に `accounts.get` を呼び、`reportingTimeZone` と `currencyCode` を得る。レポートのヘッダが示す通貨がアカウントの通貨と一致しない場合は、収集を失敗させる。

**理由:** アカウントの設定は管理画面から変更でき、設定値として持つと実態と乖離しても気づけない。毎回取得すれば、AdMob が実際に用いた区切りと通貨をエントリに記録できる。ヘッダとの照合は、通貨の既定値の扱いが変わった場合に、誤った通貨で記録することを防ぐ。

**通貨の扱い:** 原通貨はアカウントの通貨とし、JPY 以外は①の換算規則（Frankfurter）で JPY に換算する。AdMob に JPY を指定して換算させる案は、適用レートがレコードに残らず再計算できなくなるため採らない。`CURRENCY_SCALES` が定義していない通貨（JPY・USD 以外）の場合は、小数桁数を決められないため収集を失敗させる。

**タイムゾーンの扱い:** 対象日 D について、レポートタイムゾーンにおける D の収益を UTC 暦日 D のレコードへ記録し、エントリの `sourceTimezone` にタイムゾーンを記録する。按分はしない（[financial-record](../../specs/financial-record/spec.md) の対象日の規則）。

### 決定 3: エントリの形

| 項目 | 値 |
| --- | --- |
| `source` | `admob` |
| `category` | `FORMAT` の値をそのまま用いる（実測では小文字の `banner` / `interstitial`） |
| `acquisition` | `measured` |
| `revisable` | 真 |
| `currency` | アカウントの通貨 |
| `amount` | `microsValue` を 10 進小数へ変換し、原通貨の小数桁数へ ROUND_HALF_UP で丸めた値 |
| `sourceTimezone` | アカウントのレポートタイムゾーン |

`microsValue` は 64 ビット整数のため JSON では文字列で返る。浮動小数点数を経由せず、共有の 10 進演算で変換する。`category` を独自の名称へ変換しないのは、対応表の保守を避け、生応答との対応を自明に保つためである。

### 決定 4: OAuth のアクセストークンは収集ソースの生存期間だけ保持する

リフレッシュトークンを `https://oauth2.googleapis.com/token` へ送ってアクセストークンを得る。得たアクセストークンは、収集ソースのインスタンス内で有効期限の少し前まで再利用する。

**理由:** 日次実行では前日分に加えて当月内の既存の日を再収集するため、1 回の実行で AdMob の収集が最大 30 回程度呼ばれる。そのたびにトークンを取得し直すと、トークンエンドポイントへの要求が不要に増える。収集ソースは実行ごとに組み立て直すため、トークンが実行をまたいで残ることはない。

**失効時の扱い:** トークンエンドポイントが `invalid_grant` を返した場合は、リフレッシュトークンの再発行が必要である旨を理由に含めて収集を失敗させる。その他の失敗は HTTP ステータスを理由に含める。いずれも既存の部分失敗の扱いで欠測になる。

### 決定 5: スコープは `admob.report`、同意画面は本番公開とする

**スコープ:** `admob.report` は収益レポートと、パブリッシャー ID・レポートタイムゾーン・通貨の閲覧に限られ、本チェンジに必要な情報はすべて取得できる。`admob.readonly` は在庫やメディエーションの設定まで閲覧できるため採らない。どちらも閲覧専用である。

**同意画面:** 外部ユーザー向けの同意画面がテスト状態のまま発行したリフレッシュトークンは 7 日で失効する（Google Identity の OAuth 2.0 ドキュメント）。毎週の再発行は運用として成り立たないため、公開ステータスを本番にしてから発行する。利用者は開発者本人のみのため、Google の確認（verification）は受けず、同意時に表示される未確認アプリの警告を許容する。

**発行手段:** OAuth 2.0 Playground に自前のクライアント ID とシークレットを設定し、`admob.report` を指定してリフレッシュトークンを得る。AdMob API のドキュメントが案内する方法であり、発行のためのコードを持たずに済む。OAuth クライアントはウェブアプリケーションとして作成し、承認済みのリダイレクト URI に Playground の URL を登録する。

### 決定 6: 認証情報と設定値はすべて Worker のシークレットで渡す

| 名前 | 内容 |
| --- | --- |
| `ADMOB_CLIENT_ID` | OAuth クライアント ID |
| `ADMOB_CLIENT_SECRET` | OAuth クライアントシークレット |
| `ADMOB_REFRESH_TOKEN` | リフレッシュトークン |
| `ADMOB_PUBLISHER_ID` | パブリッシャー ID（`pub-` で始まる） |
| `ADMOB_APP_ID` | sizet のアプリ ID（`ca-app-pub-` で始まる） |

②の決定 6 と同じく、秘匿不要な値もシークレットに寄せて設定箇所を 1 つにする。いずれかが未設定の場合は、費用の取得元と同じく、必ず失敗する収集ソースとして登録して欠測にする。アプリ ID がパブリッシャー ID に属さない組み合わせ（`ca-app-{パブリッシャー ID}~` で始まらない）は、設定誤りとして同様に扱う。

収集ソースの組み立ては、費用とは別の関数として追加し、Worker の組み立て処理で費用の収集ソースと連結する。費用の組み立て関数の名前と責務を変えずに済む。

### 決定 7: 遡及可能期間は宣言しない

AdMob のレポートは過去日を指定して取得でき、現在の状態に依存する判定も含まない。月次クローズ（翌月 6 日）で前月の全日を再収集するには最大で約 37 日遡る必要があるが、実 API で 59 日前まで取得できることを確認した。上限は公式ドキュメントに記載がないため、上限に達した場合は取得の失敗として欠測に現れる。

### 決定 8: 生応答にはアカウント情報とレポートを保存する

`accounts.get` の応答とレポートの応答をまとめて `raw/` に保存する。トークンエンドポイントの応答（アクセストークンを含む）は保存しない。アカウント情報はパブリッシャー ID・表示名・タイムゾーン・通貨のみで、個人を特定する情報を含まない。

## Risks / Trade-offs

- **推定収益と実際の支払額の乖離** → API は推定収益しか返さず、確定額は取得できない。改訂可能性を真として推定値であることを示し、月次クローズ時点の推定値をその月の最終値とする。支払額との差は公開データからは解消できない
- **リフレッシュトークンの失効・取り消し** → 失効すると AdMob が欠測になる。理由に再発行が必要な旨を含め、実行記録から原因が分かるようにする。同意画面を本番公開にしておけば 7 日失効は起きず、日次で使うため 6 か月未使用による失効も起きない。再発行を繰り返すと、同一アカウント・同一クライアントで 100 件を超えた時点で古いトークンが無効になる
- **未確認アプリとしての運用** → Google の確認を受けないため、同意時に警告が出る。利用者が開発者本人のみであれば同意できるが、Google の方針変更で未確認アプリの利用が制限されると再発行できなくなる
- **タイムゾーンの境界のずれ** → レポートタイムゾーンが `Asia/Tokyo` の場合、UTC 暦日のレコードに 9 時間ずれた日の収益が入る。エントリに集計タイムゾーンを記録して明示する。月の境界でも 1 日が 2 つのレコードに分かれることはなく、二重計上は起きない
- **認証情報の組み合わせ** → クライアント・シークレット・リフレッシュトークンのいずれかを更新し忘れると失敗する。いずれも欠測として現れる
- **9 月の締切** → 10-06 までにデプロイできなければ、9 月の収益は恒久的に記録できない。事前作業（OAuth の準備）を実装と並行して進める

## Migration Plan

1. Google Cloud プロジェクトで AdMob API を有効化する
2. OAuth 同意画面（外部ユーザー）を作成し、スコープに `admob.report` を追加して公開ステータスを本番にする
3. OAuth クライアント（ウェブアプリケーション）を作成し、OAuth 2.0 Playground でリフレッシュトークンを発行する
4. 5 つの値を Worker のシークレットとして設定する
5. 収集ソースを実装して登録し、デプロイする
6. 手動再実行で前日を指定し、AdMob の収益エントリが記録されることを確認する
7. 翌日以降の当月中の再収集で、2026-09-08 以降の各日に収益が追加されることを確認する

ロールバックは、AdMob の収集ソースの登録を外して再デプロイすることで行う。保存済みのレコードは不変であり削除しないため、誤ったデータを記録した場合は、対象月がクローズされる前に訂正リビジョンで上書きする。
