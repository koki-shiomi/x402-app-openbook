## Context

⑤の有料 API が本番で動いており、無料の一覧・402 での支払いの条件の提示・支払い後のバイト列と `X-Anchor-*` ヘッダの返却が成立している。動機は [proposal.md - Why](proposal.md) を参照。

実測で確認した、設計を規定する事実は次のとおり。

| 項目 | 内容 |
| --- | --- |
| 有料 API の CORS | **応答に `Access-Control-*` を含まない**。別オリジンのブラウザからは読めない |
| Arc テストネットの RPC の CORS | **`Origin` を反映して許可を返す**。ブラウザから直接チェーンを照会できる |
| 決済の取次の受理条件 | 支払いの条件の `extra` が広告と一致し、署名の EIP-712 ドメインがその `extra` のとおりで、有効期間が `minValiditySeconds` 以上であること。支払い元と受取先が同一だと拒む |
| 決済に用いる残高 | ウォレットの保有残高ではなく、Circle の Gateway Wallet へ預け入れた残高を用いる。不足すると署名の後に `insufficient_balance` になる |
| 既存のクライアント実装 | `@x402/evm` の `exact` のクライアントは署名の `verifyingContract` に資産のアドレスを固定で用いるため、この取次へは支払えない |
| 静的な資産と Worker の同居 | 静的な資産が先に照合され、該当がなければ Worker が動く（公式ドキュメント） |

## Goals / Non-Goals

**Goals:**

- 有料 API で何が取得できるかを、実際に買って確かめられるようにする
- 取得したバイト列の検証が、運営者を信頼せずに成立することを示す
- 支払いが失敗する条件を、署名を求める前に示す

**Non-Goals:**

- 日次データの主たる取得経路になること。API がその役割を持つ
- 複数日の集計・推移の可視化。1 日分の明細にとどめる
- 取得した内容の保存、利用者の識別、購入履歴
- 本番チェーンでの決済。⑤と同じくテストネットに限る
- 独自ドメインの取得

## Decisions

### 決定 1: API と同一のオリジンで配る

静的な資産を API と同じ Worker から配る。画面から API へは相対パスで要求する。

**理由:** 有料 API は `Access-Control-*` を返さないため、別オリジンからは一覧すら読めない。同一オリジンなら CORS の設定を足す必要がない。さらに `PAYMENT-REQUIRED`・`PAYMENT-RESPONSE`・`X-Anchor-*` はいずれも応答ヘッダで、別オリジンから読むには `Access-Control-Expose-Headers` での個別の開示が要る。同一オリジンならその管理も不要になる。

**経路の衝突:** 静的な資産が先に照合され、該当がなければ Worker が動く。`/v1/records` は資産として存在しないため Worker へ落ちる。資産側に `v1` で始まる名前を置かない。

**検討した代替案:** 静的サイトとして別に配り、API へ CORS を足す案。公開する面が増え、どのオリジンへ何を開示するかの判断が常に必要になる。デモの規模に見合わない。

### 決定 2: フレームワークを用いず、束ね役だけを入れる

画面は 1 つで、状態は「一覧」「購入中」「明細」の 3 つしかない。UI のフレームワークは使わず、素の TypeScript で書く。`packages/shared` と viem をブラウザ向けに束ねるためだけに Vite を用いる。

**理由:** 検証関数と刻印の照会は `packages/shared` にあり、viem に依存する。これをブラウザで動かすには束ね役が要る。一方、画面の構造はフレームワークを入れて得るものが少ない。

### 決定 3: 署名は支払いの条件から組み立て、自前で行う

402 応答の `PAYMENT-REQUIRED` を復号し、`accepts[0]` の `extra` が示す EIP-712 のドメイン（`name`・`version`・`verifyingContract`）と `network` のチェーン ID で `TransferWithAuthorization` に署名する。有効期限は条件の `maxTimeoutSeconds` を現在時刻に足した値とする。署名は `eth_signTypedData_v4` でウォレットへ求める。

**理由:** `@x402/evm` のクライアントは署名の `verifyingContract` に資産のアドレスを固定で用いるため、この取次では `invalid_signature` になる。取次が広告するドメインで署名する必要があり、その値は API が条件として返している。画面に固定で持つと、取次側の変更に追従できない。

**署名する内容:** `from`（接続したアドレス）・`to`（条件の `payTo`）・`value`（条件の `amount`）・`validAfter`（0）・`validBefore`・`nonce`（乱数 32 バイト）。

### 決定 4: 支払えない条件は、署名を求める前にチェーンを読んで判定する

次の順に確かめ、満たさないものがあれば理由と必要な操作を示して署名へ進まない。

| 確認 | 方法 |
| --- | --- |
| ウォレットの接続 | 接続済みのアドレスの有無 |
| チェーン | 接続先のチェーン ID が条件の `network` と一致するか |
| 支払い元と受取先が別か | 接続したアドレスと条件の `payTo` の比較 |
| 預け入れた残高 | Gateway Wallet の残高の照会が条件の `amount` 以上か |

**理由:** 預け入れ不足と自己送金は、いずれも署名を終えて要求を送ってから取次に拒まれる。利用者は署名の手間をかけた末に、原因の分からない失敗を受け取ることになる。チェーンの読み取りは署名を伴わず、ブラウザから直接行える。

**チェーンの切り替え:** 一致しない場合は切り替えを求める。ウォレットが当該チェーンを知らない場合に備え、追加の要求も行えるようにする。

### 決定 5: 検証はチェーンを直接読み、API の応答ヘッダを根拠にしない

取得したバイト列から SHA-256 を算出し、`packages/shared` の検証関数へ渡す。刻印の照会はブラウザから Arc の RPC へ直接行う。照会先のチェーン ID とコントラクトのアドレスは画面が持つ設定値とする。

API が返す `X-Anchor-Hash` などは、画面が独自に得た値と**並べて表示する**にとどめ、判定には用いない。

**理由:** API が返した情報だけで照合すると、API の自己申告を確かめているにすぎない。照会先まで API から受け取ると、運営者が用意した別のコントラクトを指すことができてしまう。照会先を画面の設定値とし、手順書に記した値と一致していることを利用者が確かめられるようにする。

**食い違いの扱い:** 画面が持つ照会先と、API が `X-Anchor-Contract`・`X-Anchor-Chain-Id` で示す値が異なる場合は、その旨を表示する。検証は画面の設定値で行う。

### 決定 6: 取得した内容は画面の中だけに持つ

購入したバイト列と明細は変数として保持し、ブラウザの保存領域へ書かない。購入の操作の前に、保存されないことと再表示には再び支払いが必要であることを示す。

**理由:** 有料 API は利用者を識別せず、支払い 1 回につき取得 1 回である。保存すれば再表示できるが、この画面は API の内容を確かめるためのものであり、データを持ち続ける役ではない。保存しないことで、画面が公開データの別の配布経路になることも避けられる。

**利用者への影響:** 再読み込みで明細は失われる。この不便は断りを示したうえで受け入れる。

### 決定 7: 表示は 1 日分の明細に限る

購入した 1 日について、収益と費用の各エントリ、欠測、適用した為替レート、集計値、検証の結果を表示する。複数日をまたぐ集計や推移は描かない。

**理由:** 複数日を並べるには日数分の支払いが要る。⑤にまとめ買いの仕組みはなく、署名を何度も求めることになる。またこの画面の役は「API で何が取れるか」を示すことであり、レコード 1 件の中身をそのまま見せるほうが目的に合う。

**取得方式の併記:** 各エントリに取得元・取得方式・提供元が値を改訂しうるかを添える。同じ金額でも実測値と宣言値では意味が異なる。

## Risks / Trade-offs

- **[利用者の下準備が重い]** → Arc テストネットの追加・テストネット USDC の入手・Gateway への預け入れが要る。実際に買える人は限られる。デモという位置づけを画面に明示し、手順を案内する
- **[ウォレットが Arc テストネットを扱えない]** → 切り替えと追加の要求が拒まれる場合は、手動での追加に必要な値（チェーン ID・RPC・通貨）を表示する
- **[保存しないため再表示に再び支払いが要る]** → 決定 6 の帰結。購入の前に断りを示す
- **[画面と API が同居する]** → 静的な資産の追加が API の経路に影響しうる。資産側に `v1` で始まる名前を置かず、デプロイ後に API の経路が変わっていないことを確認する
- **[照会先の設定値が誤っていると検証が常に失敗する]** → 手順書に記したコントラクトのアドレスと一致していることを、実装時とデプロイ後の両方で確認する
- **[テストネットの USDC に価値がない]** → 支払いの体験は成立するが、経済的な意味は持たない。本番チェーンへ移す際は⑤と合わせて再検討する

## Migration Plan

1. `apps/web` を作成し、ワークスペースへ加える。束ね役の設定と、`packages/shared` をブラウザで動かせることを確認する
2. 一覧の表示と、支払いを伴わない画面を作る
3. ウォレットの接続・チェーンの確認・預け入れた残高の確認を実装する
4. 署名と支払い、明細の表示を実装する
5. 検証と判定の根拠の表示を実装する
6. 静的な資産の配信を設定へ加え、デプロイする。API の既存の経路が変わっていないことを確認する

ロールバックは設定から静的な資産の配信を外し、Worker を直前のバージョンへ戻すことで行う。API と保存物には影響しない。
