## Context

日次レコードは R2 の `records/{対象日}/{リビジョン}.json` に正準 JSON のバイト列として保存され、④で最新リビジョンの SHA-256 を Arc テストネットの `AnchorRegistry` へ刻印している。刻印の結果は `anchors/{対象日}/{リビジョン}.json` にあり、トランザクションのハッシュとブロック番号を持つ。現在 Worker が公開しているのは `/health` と、共有シークレットで保護した `/admin/rerun` の 2 つだけである。動機は [proposal.md - Why](proposal.md) を参照。

設計を規定する x402 と Circle の facilitator の制約は次のとおり。2026-09-16 に実測・確認した結果は [openspec/config.yaml](../../config.yaml) に記録する。

| 項目 | 内容 |
| --- | --- |
| プロトコル | x402 V2。ヘッダは `PAYMENT-REQUIRED`（サーバ→クライアント）、`PAYMENT-SIGNATURE`（クライアント→サーバ）、`PAYMENT-RESPONSE`（サーバ→クライアント） |
| facilitator | Circle hosted の `https://gateway-api-testnet.circle.com/v1/x402`。`/supported`・`/verify`・`/settle` を提供し、**API キーを要求しない**（認証なしの POST が 400「引数不足」を返すことで確認） |
| 対応するチェーン | `/supported` に `eip155:5042002`（Arc Testnet）が含まれる。scheme は `exact`、資産は USDC `0x3600000000000000000000000000000000000000`（6 桁）、`extra` は `GatewayWalletBatched`（`verifyingContract` は `0x0077777d7eba4688bdef3e311b846f25870a19b9`、`minValiditySeconds` は 604800） |
| Arc Mainnet | 公開されている facilitator に `eip155:5042` の対応はない（x402.org・Solvador・PayAI・公式一覧の各社を確認） |
| 実装 | `@x402/hono` 2.26.0 が Hono 用のミドルウェアを提供する。`@x402/core` の依存は `zod` のみで Node 固有の API を使わず、Workers で動作する |

## Goals / Non-Goals

**Goals:**

- 公開したバイト列が常にチェーン上の刻印と照合できる状態を保つ
- 利用者が取得できないものに支払わないようにする
- 決済の検証と実行を自前で持たず、標準の facilitator に委ねる
- ⑥が支払いなしで対象日の骨格を描けるようにする

**Non-Goals:**

- Arc Mainnet での決済。対応する facilitator が存在しない
- 期間指定・月次集計・過去リビジョンの提供
- 利用者ごとの識別、レート制限、利用回数の管理
- 支払いを収益として公開すること（テストネットの USDC に経済的価値がない）
- 独自ドメインの取得

## Decisions

### 決定 1: 支払いの判定より先に、取得できるかを判定する

ミドルウェアの順序を「対象日の妥当性 → レコードの存在 → 刻印の有無 → x402 の決済」とする。前の 3 つで拒む場合、x402 のミドルウェアへ到達させない。

| 状態 | 応答 |
| --- | --- |
| 対象日の形式が不正 | 400 |
| レコードが存在しない | 404 |
| レコードはあるが最新リビジョンが未刻印 | 409（刻印待ちであることと対象日を示す） |
| 刻印済み | x402 の決済へ進む |

**理由:** 支払いを求めてから存在しないと返すと、利用者が取得できないものに支払うことになる。`@x402/hono` の `onProtectedRequest` フックでも拒めるが、フックの `abort` は 403 を返す仕様で、404 と 409 を区別できない。素の Hono ミドルウェアを前段に置くほうが、応答を仕様どおりに作れる。

**未刻印に 409 を用いる理由:** 404 と区別できる必要がある。404 は「その日は存在しない」、409 は「存在するが今は取得できない、後で取得できる」を表す。利用者は再試行すべきかを判断できる。

### 決定 2: 刻印情報は応答ヘッダへ載せる

本文は `getRecord` が返すバイト列をそのまま渡し、刻印の情報は `X-Anchor-*` の応答ヘッダで添える。

| ヘッダ | 内容 |
| --- | --- |
| `X-Anchor-Revision` | 刻印されたリビジョン番号 |
| `X-Anchor-Hash` | 刻印された SHA-256（`0x` つき） |
| `X-Anchor-Chain-Id` | チェーン ID |
| `X-Anchor-Contract` | コントラクトのアドレス |
| `X-Anchor-Transaction` | トランザクションのハッシュ |
| `X-Anchor-Block` | ブロック番号 |

**理由:** 本文へ混ぜるとバイト列が変わり、SHA-256 が刻印と一致しなくなる。ラップした JSON（`{record: ..., anchor: ...}`）で返す案は、利用者が `record` の部分を取り出して再直列化するとバイト列が変わるため採らない。ヘッダなら本文は 1 バイトも変わらない。

**トランザクションのハッシュがない場合:** ④の突き合わせで「刻印済みと確認したが送信はしなかった」リビジョンは、トランザクションのハッシュとブロック番号を持たない。この 2 つのヘッダを省略し、他は載せる。

**`Content-Type`:** `application/json` とする。本文は正準 JSON である。

### 決定 3: 一覧は `anchors/` の一覧から作る

無料の一覧は、R2 の `anchors/` のキーを列挙して対象日ごとの最大リビジョンを求め、対象日の降順で返す。`records/` は見ない。

**理由:** `anchors/` にあるということは刻印済みであり、そのまま「取得可能な日」の定義になる。`records/` と突き合わせる必要がない。④の [targets.ts](../../../apps/api/src/anchor/targets.ts) が同じ形のキーを列挙しているため、列挙の処理を共有できる。

**金額を含めない:** 対象日とリビジョン番号のみとする。金額を含めると、一覧だけで収支の概形が分かり、有料のレコードを取得する意味が薄れる。

**件数の上限:** 稼働 1 年でも 365 件程度で、R2 の一覧 1 ページに収まる。ページ送りは設けない。

### 決定 4: x402 は `@x402/hono` の設定ベースのミドルウェアを使う

`paymentMiddlewareFromConfig(routes, facilitatorClient, schemes)` を、レコードの取得パスにのみ適用する。scheme は `@x402/evm` の `ExactEvmScheme` を `eip155:5042002` に登録する。

**理由:** 自前で `PAYMENT-REQUIRED` の組み立て、`PAYMENT-SIGNATURE` の解釈、facilitator の呼び出し、`PAYMENT-RESPONSE` の付与を書くと、プロトコルの改訂に追従し続ける必要がある。Coinbase が保守するミドルウェアに委ねる。

**facilitator との起動時の同期:** `syncFacilitatorOnStart` は既定値の `true` のまま用いる。Worker では isolate ごとに起動が起きるため、その都度 facilitator の `/supported` を読み直す呼び出しが発生するが、facilitator 側が `extra`（`verifyingContract` など）を変更した場合に自動で追従できる利点を優先する。`extra` を自前でハードコードすると、Circle 側の変更に気づけないまま決済が成立しなくなる恐れがある。isolate の起動頻度に対して 1 回の HTTP 呼び出しは軽く、決済の成立に影響しない範囲と判断する。

**検討した代替案:** 自前で verify/settle を実装する案。Arc の USDC は EIP-3009 に対応しており（`DOMAIN_SEPARATOR` と `authorizationState` の応答を実測）技術的には可能だが、二重支払いの防止・手数料の負担・nonce の管理を自前で持つことになる。利用者が運営者 1 名の規模では見合わない。

### 決定 5: 設定はシークレットで渡し、価格と受取先を設定値にする

| 名前 | 内容 |
| --- | --- |
| `X402_FACILITATOR_URL` | facilitator の所在 |
| `X402_PAY_TO` | 受取先のアドレス |
| `X402_PRICE_USDC` | 1 日分の価格（既定 `0.10`） |

②の決定 6 と同じく、秘匿不要な値もシークレットに寄せて設定箇所を 1 つにする。いずれかが未設定の場合、有料のエンドポイントは支払いを求められず 503 を返し、一覧と `/health` は通常どおり動く。決済の設定がないまま無料でレコードを配ることは避ける。

**受取先を刻印用の EOA と兼用する:** 新たな秘密鍵を増やさない。受取だけなら署名は不要で、Worker に秘密鍵を持たせる必要もない。刻印用の鍵が漏洩しても、受け取った USDC を持ち出されるだけで、刻印の履歴は書き換えられない。

### 決定 6: 支払いの明細は R2 へ 1 件ずつ保存する

`payments/{対象日}/{成立時刻}.json` に、成立時刻・対象日・金額・資産・ネットワーク・支払い元のアドレス・トランザクションのハッシュを保存する。

**理由:** 対象日ごとに引けると、⑥で「この日は何回買われたか」を示せる。時刻をキーに含めるため、同じ日への複数回の支払いが上書きされない。

**書き込みの失敗:** 明細の保存に失敗しても、本文は返す。決済は既に成立しており、本文を返さないと利用者が支払い損になる。失敗は記録に残すのみとする。

**収益に含めない:** 収集ソースとして登録しない。テストネットの USDC には経済的価値がなく、収益として公開すると実態を誤らせる。本番チェーンへ移すときに改めて決める。

### 決定 7: エンドポイントの構成

| パス | 認証・課金 | 内容 |
| --- | --- | --- |
| `GET /v1/records` | 無料 | 取得可能な対象日とリビジョン番号の一覧 |
| `GET /v1/records/{date}` | 有料 | 当該日の最新リビジョンのバイト列 |
| `GET /health` | 無料 | 稼働確認（既存） |
| `POST /admin/rerun` | 共有シークレット | 手動再実行（既存） |

**`/v1` を付ける理由:** 公開する API は後方互換を壊しにくい。レコードの形式は `schemaVersion` で表すが、エンドポイントの構成が変わる場合に備えて版を分けられるようにする。

**API ドキュメント:** `/health` と `/admin/rerun` を含めない。前者は利用者に意味がなく、後者は運営者専用である。

## Risks / Trade-offs

- **[前日分がしばらく取得できない]** → 日次実行は収集の直後に刻印するため通常は数秒だが、刻印が失敗すると次の実行まで 409 が続く。検証可能性を優先する方針の帰結として受け入れる。409 の本文で刻印待ちと分かるようにする
- **[facilitator への依存]** → Circle の facilitator が停止すると決済が成立せず、有料のエンドポイントが使えなくなる。一覧と `/health` は影響を受けない。所在を設定値にして切り替えられるようにする
- **[Arc Mainnet へ移せない]** → 対応する facilitator が存在しない。本番チェーンへ移すときは、自前の facilitator か別のチェーンでの決済を検討する必要がある
- **[GatewayWalletBatched 固有の仕組み]** → 素の EIP-3009 ではなく Circle Gateway の仕組みを前提とする。有効期間の下限が 7 日（604800 秒）と指定されており、支払いの署名が長く有効になる。利用者側のクライアントも同じ仕組みに対応している必要がある
- **[明細の保存漏れ]** → 決済が成立したのに明細を保存できないと、売上の記録が欠ける。公開データではないため影響は限定的で、失敗を記録に残すにとどめる
- **[支払い済みの利用者が再取得できない]** → 1 回の支払いで 1 回の取得とする。取得に失敗した場合、利用者は再び支払う必要がある。利用者ごとの識別を持たない設計の帰結である

## Migration Plan

1. `@x402/hono`・`@x402/core`・`@x402/evm` を `apps/api` へ追加する
2. 一覧・レコードの取得・刻印情報の付与を実装する（決済なしで動作を確認できる）
3. x402 のミドルウェアと支払いの明細を組み込む
4. 3 つのシークレットを設定してデプロイする
5. 支払いなしで一覧を取得し、刻印済みの日で 402 が返ることを確認する
6. 実際に支払って本文と刻印情報が返り、SHA-256 が刻印と一致することを確認する
7. 未刻印の日で 409、存在しない日で 404 が支払いなしに返ることを確認する

ロールバックは Worker を直前のバージョンへ戻すことで行う。保存済みのレコードと刻印には影響しない。既に成立した支払いは取り消せないが、返す内容が変わるだけで検証には影響しない。
